* Two traps that cost an hour each

** Narinfo URLs take the digest, not the store path name

=http://silver.lan:5000/z8hfiv…-nixos-system-misfit-26.11pre-git.narinfo= is a 404
and looks exactly like "Harmonia is broken". The route takes the 32-character
digest only; harmonia 3.3.0 runs =StorePathHash::decode_digest= over whatever is
in front of =.narinfo= and rejects the longer string with
=Invalid hash format: invalid store path hash length=:

#+begin_example
$ curl -s http://127.0.0.1:5000/z8hfiv711flpm142yp6p33yraf2nmlfl.narinfo | grep Sig
Sig: silver-1:lr9aW+...
#+end_example

** Nothing has to run to publish a warmed closure

=harmonia-cache= reads =/nix/var/nix/db/db.sqlite= per request, so a path that
lands in the store is substitutable immediately. =harmonia-gc.service* is
retention only (=delete-older-than=, =ensureFree=) and runs weekly; the first
run after the roots appeared printed "350.63 GiB already free, nothing to do"
and changed nothing. There is no index step to trigger after =just cache-build=.

* Four things the plan got wrong

** The drv to warm is the hive's, not the flake's

=cache-build-one= started as =nix eval --raw ".#<host>.drvPath"=. That is
=nixosConfigurations.<host>.config.system.build.toplevel=, built from the
flake's own =meta.nixpkgs=. =just remote-apply= installs
=colmenaHive.nodes.<host>.config.system.build.toplevel=, which imports
=meta.nixpkgs= *and* =meta.nodeNixpkgs= and is a different derivation:

#+begin_example
flake closure  nixos-system-misfit-26.11.20261017.9e91791.drv
hive  closure  nixos-system-misfit-26.11pre-git.drv
#+end_example

Nothing is shared between the two, so warming the flake closure makes a deploy
substitute exactly nothing and leaves the wrong closure GC-rooted. Fixed by
trying the hive path first and falling back to =.#<host>= for the darwin hosts,
which have no hive node. =dgx-spark= shows the same split:
=nixos-system-dgx-spark-26.11pre-git= from the hive versus
=nixos-system-dgx-spark-26.11.20260928.5200201= from the flake.

** =builders-use-substitutes = false= makes builders compile what they could fetch

The plan set this so "silver sends the inputs". It does more than that: the
builder may not use *any* substituter for that build. The aarch64-linux CUDA
paths that dgx-spark normally pulls from =cache.nixos-cuda.org=,
=graham33.cachix.org= and =ai.cachix.org= were compiled from source instead.
Set it to =true= (Nix's own default). Substituted inputs still reach silver,
because the outputs that reference them are copied back.

** =maxJobs = 1= does not limit one build

=buildMachines.maxJobs= is the scheduler's view of how many drvs silver hands
to a machine at once. A single drv is then free to use every core the builder's
daemon allows. The first dgx-spark run reached load 38 on 20 cores — 20 =nvcc=
plus 20 =ptxas= — while =tensorfold-nati= held 86 G of the box's 121 G RAM with
34 G spare. That is an OOM waiting to evict the model.

The knob is on the *builder*: =nix.settings.max-jobs = 1= and
=nix.settings.cores = 8= in =hosts/dgx-spark/configuration.nix=. Both are in
=/etc/nix/nix.conf= now.

A cgroup guard (=MemoryMax= on =nix-daemon=) does not help here: ssh-ng builds
are spawned by the =nix-daemon --stdio= child under the sshd session cgroup,
not the =nix-daemon.service= cgroup.

** The gcroots directory is created per-user, not globally

=--add-root= writes =/nix/var/nix/gcroots/cache/<name>= as the user running the
trigger (=yuanw=), while =harmonia.gc.gcRootsDirs= points at the global
directory. Created it with =systemd.tmpfiles= as =root:wheel 0775= so the
non-root trigger can write it and the daemon-owned GC can read it.

* The Spark

dgx-spark stays a declared builder — it is the only =aarch64-linux= machine —
but it is out of the default =cache-targets= list. Its closure compiles CUDA
from source because =cuda-fixes.nix= patches libnvshmem for CUDA 13.2, so no
public cache has that drv. One attempt ran 60+ minutes and was killed; the
model kept its 86 G.

Run it deliberately, when inference is idle:

#+begin_example
just cache-build-one dgx-spark
#+end_example

* The deploy is a CUDA build

`hosts/dgx-spark/default.nix:45` is `buildOnTarget = true`, so a pin bump
compiles on the inference box as part of `just remote-apply`. Measured on the
first bump after merging main: magma alone is 3492 build steps
(`[1497/3492] Building CUDA object CMakeFiles/magma.dir/magmablas/
spotf2_kernels_var.cu.o`), then ucc/ucx, and my 900 s client timeout fired while
it was still going. Nix's client died; the builder finished magma anyway.

Two things keep that survivable:

- `nix.settings.cores = 8` on dgx-spark held the deploy build at load 8.8 on a
  20-core box with the model resident (measured, same run).
- The slice that actually holds the builds is `user-<uid>.slice` — user slices
  are named by UID, so a `user-yuanw.slice` unit is never instantiated and does
  nothing (checked against `/proc/<ninja>/cgroup`: sessions land in
  `/user.slice/user-1000.slice/session-512.scope`). It took three attempts to
  write it declaratively:
  1. `systemd.units."user-yuanw.slice"` — wrong name, never instantiated.
  2. `systemd.units."user-1000.slice"` and `systemd.slices."user-1000"` — nixpkgs
     folds the instance into the `user-.slice` template and **emits no file**;
     neither appeared in the `system-units` output or `/etc/systemd/system`.
  3. `environment.etc."systemd/system.control/user-1000.slice.d/50-lan-build-guard.conf"`
     — where systemd actually looks and where `systemctl set-property` writes its
     own persistent state. This is what is deployed.
  Also do not build the path from `config.users.users.yuanw.uid`: that option is
  `null` on this host (the UID comes from the hardware config), so it silently
  produced `user-.slice.d` and applied to nothing. `id yuanw` is uid=1000.
- The settings themselves: `CPUWeight=20`, `MemoryHigh=32G`, `MemoryMax=40G`.
  Weight bounds contention; the cap bounds the disaster — torch put four `cicc`
  at 4 G each on the box with 17 G spare and the 86 G model resident, so without
  it the OOM killer picks the biggest RSS, which is the model.
- `systemctl set-property user-1000.slice MemoryMax=40G` applies that ceiling
  *live*, which is what you want mid-build: `cores` is read when the build
  starts, so lowering it cannot stop a build already running, and waiting for the
  deploy to activate is too late. It is also the way to check the numbers work
  before committing to the unit-file route.

`ptxas` died on signal 11 compiling nvshmem's `reducescatter_and.cu` once,
which is the failure the plan predicted for CUDA. It is not reproducible — the
running system already carries `libnvshmem-3.8.0-0`, so the same drv built here
before — and a plain retry got through it. Treat the first ptxas failure as
transient and re-run; treat the second as a real bug.

* Why the CUDA outputs also go to Cachix

`just cache-push` uploads the CUDA / torch subset of silver's copy of the
Spark's closure to `dgx-spark-nixos.cachix.org`, which dgx-spark substitutes
from (priority 41, behind silver's 10).

For a LAN host silver alone would do: every host already trusts `silver-1`. The
push earns its place on three other counts.

1. **Nobody else moves the outputs.** With `buildOnTarget = true` the deploy
   builds on the Spark and the results stay there. Silver never sees magma
   unless something copies it. That copy is the whole job of this recipe.
2. **Retention.** silver's Harmonia GC is `deleteOlderThan = 30d` /
   `keepRecent = 1d` / `ensureFree = 50G`, and the root I create is one symlink
   per host pointing at the *current* toplevel, so magma is only rooted while it
   is current. A few bumps later it is unrooted and low free space reclaims it.
   `harmonia-store-gc` builds its keep-set purely from the gcroots dirs
   (`gc.rs:300`), so nothing outside them is protected. Cachix expires nothing.
3. **One copy is not a backup.** silver is a MacBookPro11,5 with the store on a
   single internal SSD; if it dies the only magma is on the Spark, which runs
   its own weekly `nix.gc --delete-older-than 30d`. And off-LAN — travelling
   mist, asche, CI — there is no route to `silver.lan` at all.

The alternative considered and rejected: harvest to silver and pin the CUDA
paths with extra gcroots (no token, LAN speed, never collected). Same traffic,
but single-copy and unreachable off the LAN.

Filter: upstream CUDA and torch names only (`cuda|nvshmem|magma|cudnn|nccl|…`).
The cache is public, so our own outputs — tensorfold's Zig engine, vllm-aeon —
stay out of it deliberately.

The push token lives in pass at `cachix/dgx-spark-nixos` and is encrypted for
silver by hand into `secrets/cachix-auth-token.age`;
`modules/services/cache/push.nix` enables the secret only when that file exists,
so the repo deploys either way.

Two things about pushing that are not obvious:

- =nix copy --to https://<cache>.cachix.org= fails with =Method not supported=.
  The binary-cache HTTP protocol is read-only; uploading is the CLI's job, so
  the recipe runs =cachix push= on silver (installed by the same module) with
  =CACHIX_AUTH_TOKEN= from the agenix path.
- What gets pushed is the *runtime* closure — 49 paths: nvshmem, torch, the
  =cuda13.2-*= libraries — and that is verified in the cache:

  #+begin_example
  $ curl -s https://dgx-spark-nixos.cachix.org/zsdks…-cuda13.2-libnvshmem-3.8.0-0.narinfo | grep Sig
  Sig: dgx-spark-nixos.cachix.org-1:lR85Ufsiy5CPs0DpISSZtyXLMWqtb/+Mjg4jzyq6mWO…
  #+end_example

  which is the key in dgx-spark's =trusted-public-keys=, so the Spark substitutes
  it rather than compiling.

  The gap: magma was not pushed. It is a build-time input, so it is in no
  closure =nix-store -q --requisites= can walk, and the toplevel =.drv= is not
  valid on either box (=keep-derivations= is on silver but the closure arrived by
  =nix copy=), so there is nothing to enumerate. magma will still rebuild on a
  bump. If that starts costing real time, the fix is to keep the drvs on the
  Spark and build the push list from the =.drv= closure instead of the output
  closure.

* Left as the plan said

- No global =nix.settings.max-jobs = 0= on silver. =buildOnTarget = true= means
  a silver deploy builds on silver itself, and =max-jobs = 0= would make every
  silver deploy depend on misfit being up. The trigger passes =--max-jobs 0=
  instead, which costs nothing when nothing is deployed.
- =keep-derivations= and =keep-outputs= are *on* on silver
  (=modules/services/cache/harmonia.nix=), so the closure and its drvs survive
  even if the GC runs; the gcroot is what keeps them reachable in the first
  place. Deleting =/nix/var/nix/gcroots/cache/<host>= is what makes a warmed
  closure collectable.
- =nix.publicHostKey= wants the whole =ssh-ed25519 AAAA...= line base64'd, not
  the bare key blob. The first attempt used the blob and nix fell back to
  interactive host key approval, which hangs a build with no tty.
