* Goal

Try upstream TensorFold's *Zig* engine (1.0.0 = =tensorfold-native=) on the
single DGX Spark, serving Qwen3.8 Flash Next over an OpenAI-compatible API
on :8888, then run the *same* Spark-Bench suite already used against the
Python TensorFold and red-snow deployments so all three are comparable.

* Why now

- The repo's current =packages/tensorfold= pins the *Python* engine:
  =ashhart/TensorFold= @ =17c73e1= (v0.6.1), served via =python3-env=.
- Upstream has since become a Zig binary (repo language: Zig; 1.0.0
  "serves language models from a Zig binary … no Python or MLX at serve
  time"). Upstream 1.0.0 qualifies Flash Next on *Metal* only; the CUDA
  single-Spark path is the gated branch =zig-flashnext= plus the CUDA
  family registry from [[https://github.com/ashhart/TensorFold/pull/443][PR #443]] (=59e77e8=).
- MiaAI-Lab packaged exactly that path (container + ~9 patches) for a
  single GB10; it is the reference deployment to copy.

* Routes

*** A — run the MiaAI-Lab recipe as-is (fallback/sanity check)
Clone the recipe on the Spark, =scripts/prepare.sh= (image + checkpoint),
=./start.sh=. Least work; validates the engine and gives the benchmark.
Risks: =docker=-vs-podman differences, group/permissions, GHCR pull,
image build (Zig + patches) time.

*** B — extract the image's engine into the Nix store (middle path)
Pull the prebuilt (or locally built) =tensorfold-qwen38:zig-…= image and
lift =/opt/tensorfold/{bin,lib,share}= into a fixed-output derivation, then
run =tensorfold-native= from a Nix systemd unit (no container at serve
time) with =TENSORFOLD_CUDA_KERNELS= pointing at the extracted =sm121=
cubins. Mirrors how the repo treated the old containers as toolchain
suppliers. Fiddly: CUDA runtime libs / =RUNTIME.md=.

*** C — fully native Nix build (recommended target; see feasibility below)
Package =zig_0_17= from nixpkgs, apply =patches/0001…0009= to =TF_REF=,
=zig build fatbins install native= with nixpkgs =cudaPackages= nvcc, and
reproduce the Triton AOT capture with nixpkgs =python313Packages.{torch,triton}=
(=tools/zig/flashnext_aot.py=). Ship the binary + =sm121= cubins in the
store and point =TENSORFOLD_CUDA_KERNELS= at them. This is the goal;
Routes A/B are a quick engine sanity check and a fallback.

** Native feasibility — verified (2026-10-09)

Reading the recipe's Dockerfile (=scripts/prepare.sh=) against nixpkgs,
a container-free build is viable:

- *Zig*: nixpkgs ships =zig_0_17= = 0.17.0 (aarch64-linux) — the exact
  =.zig-version= pin. No tarball fetch needed.
- *Engine*: clean =TF_REF= checkout + =git apply patches/*.patch=, then
  =zig build -Dnvcc=<nvcc> -Doptimize=fast --prefix … fatbins install native=
  (=fatbins= = sm_121 SASS via nvcc; no GPU at build time).
- *Triton AOT*: =PYTHONPATH=src python -B tools/zig/flashnext_aot.py build
  --spec zig/tests/cuda/flashnext/kernels.json --jit zig/tests/cuda/flashnext/jit.json
  --tp 1 --out …/share/tensorfold/cuda/sm121=, run *during* =docker build=
  (no GPU). Reproducible with nixpkgs =python313Packages.{torch,triton}=;
  =KERNEL_SOURCE_MTIME= only pins source mtimes for reproducible cubins.
- *Runtime*: =TENSORFOLD_CUDA_KERNELS=<…/cuda/sm121>=; CUDA libs from
  =cudaPackages= + =/run/opengl-driver/lib=; vision helper (Pillow, PyAV,
  =transformers==5.17.0=) via =TENSORFOLD_VISION_PYTHONPATH= — text-only
  (=VISION=0=) can ship first, since the Spark-Bench domains are text.

Only open risk: matching the container's Triton version closely enough
that the AOT cubins are equivalent (byte-identical is not required; the
engine only needs a valid captured set). The build needs no GPU, so it can
run while a model is still serving.

*** DONE 1a spike (2026-10-09): the native build works

Run by hand on the Spark, no container:

- =zig build -Dnvcc=<nvcc> -Dsm=121 fatbins= → every CUDA fatbin
  (experts, gdn, int4, fn_qmm*, prefill_attention, scan_rows, torch_*).
- =zig build … install native= → =tensorfold-native= (22.7 MB);
  =capabilities --json= reports =engine zig=, =chip nvidia-sm121=,
  family =qwen4_exp= (=gptq-b4=) — the INT4-AutoRound format.
- =tools/zig/flashnext_aot.py build= → 320 Triton cubins + =aot.json=.

Three things the container hides:

1. *nvcc needs a header wrapper.* =cuda_nvcc= alone has no
   =cuda_runtime.h=; the merged CUDA home (nvcc + crt + cudart + cccl + …)
   supplies it, so nvcc is invoked as =nvcc -I<cudaHome>/include=.
   =packages/tensorfold-zig/default.nix= ships that wrapper.
2. *The AOT spec records the container's paths.* =kernels.json= hardcodes
   =source_root=/tensorfold/src= and the triton
   =…/dist-packages/triton/…/libdevice.10.bc= for all 421 kernels; both
   must be rewritten to the build's paths — the tool refuses otherwise.
3. *The cubins are not byte-identical.* With nixpkgs torch 2.13 + triton
   3.7.1 the capture compiles all 320 kernels but 0 match the container's
   cubin sha and 202 report drift (=cubin sha256= and =Triton hash=). The
   recipe tolerates cubin-sha drift but not Triton-hash drift, so the next
   step is to prove the engine *accepts* this capture at serve time
   (=TENSORFOLD_CUDA_KERNELS=), or match the container's exact triton.

Scaffolded: =packages/tensorfold-zig/{src.nix,default.nix}= (first cut, not
yet =nix build=-validated) with the pinned sources + the Zig 0.17.0 tarball.
Remaining: validate the package, add =modules/tensorfold-zig.nix= (port
8890 so the Python unit keeps 8888), runtime smoke, then Phase 3.

* Comparability caveats

- *Different checkpoint.* Zig serves INT4-AutoRound (top-5 experts, 4.8B
  active); its authors note ~10 % lower general capability than the
  full-expert model. A lower Spark-Bench score than the Python run does
  not mean the Zig engine is worse.
- Same harness limits as before: 75/80 scenarios, =--skip-golden-gate=,
  =LG-01= and =visual= unavailable without Playwright/Chromium.
- FP8 KV is lossy (~98.8 % top-1 agreement with bf16); use =KV_DTYPE=bf16=
  if exactness matters more than cache size.
- =THINKING=1= is the recipe default; the bench sends
  =enable_thinking=false= — verify the Zig server honours it (the README
  says request fields override serve flags).
- The Spark-Bench leaderboard's "TensorFold Zig" row is a *different*
  config (Qwen3.8 Flash Next *NVFP4*, 2 Sparks TP2, 77.9) — not this run.

* Risks / unknowns

- =docker= on this host may be podman-docker with CDI; the recipe assumes
  Docker. Phase 0 must resolve this before Phase 1.
- GHCR prebuilt image may not exist for the pinned =TF_REF=; a local image
  build compiles Zig + patches.
- Fresh ~122 GiB checkpoint download; both checkpoints together plus the
  image want ~150 GB (3.2 TB free, fine).
- One-model-at-a-time on 128 GB: the Zig boot needs ~92 GiB =MemAvailable=
  and the recipe refuses below =MEM_FLOOR_GIB= 10.
