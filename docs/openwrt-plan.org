* TL;DR

Port Mic92's [[https://github.com/Mic92/dotfiles/tree/main/openwrt][nix-uci]] idea (~230 LoC of Python + ~40 lines of nix glue, MIT,
unpacked in nixpkgs) into this repo:

  nix modules -> JSON -> generated shell script that emits ~UCI batch commands ->
  ssh | uci batch

Deltas from upstream: =rage=/age= instead of =sops= (this repo uses agenix, no
=sops= installed), a per-router config under =openwrt/=, and =just= targets that
use uci's native stage/review/commit split instead of blind apply.

First wins are low-risk, additive settings (hostname, dropbear, wifi, ddns).
Network/firewall only after the rollback path is proven.

* What the upstream mechanism actually does

~openwrt/nix/default.nix~ :

#+begin_src nix
writeUci configuration =
  let res = lib.evalModules { modules = [ module-options configuration ]; };
      json = (formats.json {}).generate "uci.json" { inherit (res.config.uci) settings secrets; };
  in { inherit json; command = writeShellScript "uci-commands" "${nix-uci}/bin/nix-uci ${json};"; }
#+end_src

~nix_uci/__init__.py~ walks that JSON and emits commands for ~uci batch~
([[https://openwrt.org/docs/guide-user/base-system/uci#uci_dataobject_model][dataobject model]]):

- named section: ~delete cfg.sec~ then ~set cfg.sec=<type>~ then one ~set~ per option
  -> *declared* sections are fully replaced, undeclared sections in the same file
  are left alone (additive management, unlike rsyncing whole =/etc/config= files).
- list option: one ~add_list~ per element.
- anonymous/list section (=config foo = without a name, e.g. =firewall= zones,
  =dhcp.host=, =ubootenv=): the caller wipes the type first
  (~while uci -q delete cfg.@foo[0]; do :; done~), then ~add cfg foo~ N times, then
  ~set cfg.@foo[i].opt= — deletion by index is not reliable, see "What the diff really
  compares".
- secrets: ~"@key@"~ in any value is filled from the JSON file named by
  ~$NIX_UCI_SECRETS~, written by the =just= recipe at apply time (=pass
  openwrt/wifipw= here). The plaintext never enters the nix store, and an
  empty value is a hard error rather than an open access point.
- ~uci.raw~: verbatim commands emitted after everything else, for what the typed
  model cannot say — =reorder firewall.@rule[i]=N to fix rule precedence, =rename= to
  name a section. No =uci= prefix; only set/add/add_list/del_list/delete/rename/reorder
  are accepted, so a stray shell command or a =commit= in the config is a build error.
  =reorder= and =rename= both exist on this box (=uci help=).
  Imperative: it reruns every time, so use it once and take it back out.

Apply path (upstream ~Justfile~):

#+begin_src makefile
eval-config: "$(nix build --no-link --print-out-paths ../#openwrt-example)"
apply: just eval-config | just ssh 'uci batch; uci commit'
#+end_src

Known upstream bug: deleting an anonymous list section is not reliable — the
loop only clears 10 entries, so more than 10 leftovers survive. Matters for
=firewall.rule=/=redirect=, =dhcp.host=, =dropbear=, =network.device=.

** secrets: `pass`, not sops and not (yet) age

`pass` is already installed and the entry already exists (`~/.password-store/openwrt/wifipw.gpg`), so the shortest path is to skip encryption files entirely. =nix_uci= needs only a =dict[str, str]=; drop the sops coupling and have it read a plain JSON file instead:

#+begin_src python
# load_sops_file(path) -> load_secrets(path): json.loads(path.read_text())
#+end_src

The justfile is what knows about the backend, and it is one line away from any
other source. Current mapping:

| placeholder     | source                  | note                                  |
|-----------------|-------------------------|----------------------------------------|
| =wireless_key=    | =pass openwrt/wifipw=     | 21 chars, verified against =/etc/config= |
| (unused)          | =op://Shared/NoneAndVoid/wireless network password= | *empty*, do not use   |

#+begin_src makefile
# in openwrt-eval: gpg-agent may prompt for a PIN the first time each session
psk=$$(pass openwrt/wifipw)
test -n "$$psk" || { echo 'empty wifi key from pass openwrt/wifipw' >&2; exit 1; }
printf '{"wireless_key": "%s"}\n' "$$psk" > "$$secrets"
#+end_src

** Guard: a blank secret is not an error.

=op read= of a field that exists but is empty prints nothing *and exits 0*, and a
failed =pass= read inside =$(...)= is just an empty string. Either way
=wifi=$$(...)= happily yields "", and an empty =wireless.@wifi-iface.key= is an
open AP or a broken network, applied with a green exit code. Hence both the
=psk= check above and the guard inside ~interpolate~:

#+begin_src python
if not val: raise ConfigError(f"secret {name} resolved to empty string")
#+end_src

If a router ever has to be configured without =op= (CI, a fresh machine), keep

** apply workflow (this is where we do better than upstream)

~uci batch~ *stages* into ~/tmp/.uci~; =uci commit= persists. So a review step is
free:

#+begin_src makefile
# stage + show what would change, commit nothing
openwrt-diff router="mist-router":
  #!/usr/bin/env bash
  set -euo pipefail
  batch="$(nix build --no-link --print-out-paths .#openwrt-{{router}})"
  "$batch" | {{ssh root@{{router}}}} 'uci batch'
  {{ssh root@{{router}}}} 'uci changes'

# stage, show, wait for confirmation, commit
openwrt-apply router="mist-router":
  just openwrt-diff {{router}}
  read -r -p "commit? "
  "$batch" | {{ssh root@{{router}}}} 'uci batch && uci commit && sync'
  {{ssh root@{{router}}}} 'for s in network wireless firewall system; do [ -x /etc/init.d/$s ] && /etc/init.d/$s reload; done'

openwrt-revert router="mist-router":
  {{ssh root@{{router}}}} 'uci revert'
#+end_src

Rules that keep this boring and safe:

- one =uci batch= at a time, no parallel applies (=uci commit= is global state).
- never apply and reload in one unreviewed shot. =uci revert= is the undo.
- =network=, =wireless= and =firewall= reloads *will* drop the ssh session and can
  lock you out. Everything else (system, ddns, dropbear, cron, luci) is safe.
- backup before any =network=/=firewall= apply:
  =ssh root@r "sysupgrade -b /tmp/backup-$(date +%F-%H%M).bin"= then =scp= it out.
- a risky apply arms a rollback =watchdog= first: it snapshots =/etc/config= to flash,
  waits 90 s, and restores it unless the router has answered ssh by then. It is armed
  only when the change touches =network=, =wireless= or =firewall= (=OPENWRT_FORCE_ROLLBACK=1=
  forces it for testing). There is deliberately no boot-time hook: =/tmp= is RAM, so the
  watchdog cannot cover a power loss mid-apply. =openwrt/state/<router>/live= is the
  manual path back for that, and =sysupgrade -b= must be =scp='d off the box to count.
  The failsafe button is *not* part of this story yet, and should not be leaned on;
  see *Failsafe rehearsal*.
- the generated batch prints plaintext secrets: never pipe it to a log file, and do
  not =grep= its output either — the wifi key scrolls right past.

** drift detection (cheaper than a diff engine)

~openwrt/state/<router>/live/*= checked into git, with secrets replaced by =@name@=
placeholders. =openwrt= has busybox =tar= and no =rsync=, so the copy is a tar pipe:

#+begin_src makefile
openwrt-facts:
    ssh root@{{router_host}} 'tar cf - -C /etc/config .' | tar xf - -C openwrt/state/{{router}}/live
#+end_src

=git diff= against that is the "what did I change in LuCI last week" answer, and
=just openwrt-diff= is the "what will this apply change" answer. Two different
questions, no clever code needed for either.

Caveat found on 2026-10-11: once =openwrt-apply= has touched a config, that file
rewrites itself — comments are dropped and every value comes out quoted, so
=option input REJECT= becomes =option input 'REJECT'=. =openwrt-diff= still reads it
as clean, but =git diff openwrt/state/= does not. Expect cosmetic churn in the snapshot after
any apply, and read the diff as *content* rather than as line-for-line.

* Phase 1/2 status (applied, in daily use)

Landed: `openwrt/` (vendored nix-uci + glue + `routers/e8450.nix`),
`packages.openwrt-e8450`, and `just openwrt-{eval,diff,apply,revert,facts}`.
`python3 openwrt/selfcheck.py` covers the serialization rules. Applied: timezone
(Regina, as the POSIX string `CST6` — the image has no `/usr/share/zoneinfo`, so
`America/Regina` would parse as UTC), wifi SSIDs/keys, dropbear. All fourteen configs
in `/etc/config` are now declared, so `openwrt-diff` is a complete drift check.
`network` and `firewall` are declared but never applied by a routine run.

Two traps hit while building it, both worth remembering:

- **nix cannot see untracked files in a git worktree.** `nix build .#openwrt-e8450`
  failed with "No such file or directory" on `openwrt/flake-module.nix` because nix
  enumerates a `path:` flake source with `git ls-files`; `?? openwrt/` is invisible.
  A brand new directory needs `git add` before it builds. This will bite any new
  module directory.
- **`uci revert` needs a config argument**, and `uci commit` with none commits every
  pending delta on the box. Both recipes now loop over the declared configs only —
  the router had a stray uncommitted `dhcp` delta that is not ours to commit or undo.
- **applies were committing without reloading, until 2026-10-11.** `changed` came from a
  plain `diff`, whose change markers are `<` and `>` rather than `+` and `-`, so the sed
  that extracted config names never matched, the reload loop never ran, and every apply
  was file-level only. It went unnoticed because the configs we applied were already
  what the router was running, and the one case that looked wrong (timezone) had been
  reloaded by hand that day. A test firewall rule proved it: present in
  `/etc/config/firewall`, absent from `nft list ruleset`. Fixed by deriving `changed`
  from the sorted *unified* diff. Anything that depends on "the apply reloaded it" is
  false before that date.

Unlocked: the first =just openwrt-eval= needs =gpg-agent= unlocked so =pass= can
decrypt =openwrt/wifipw= (once in any terminal it stays unlocked a while).

### What the diff really compares

=uci batch= has no dry run, so =openwrt-diff= applies the batch to a *materialized
copy* of =/etc/config= under =/tmp=: copy, wipe the anonymous types, =uci -c <copy>
batch=, =uci -c <copy> commit= inside the copy, then =uci show= and diff. Staging the
real configs and reverting them was wrong: the revert does not always unwind
anonymous sections, and repeated previews grew extra =@host[3]= sections. Traps found
by running it:

- **anonymous sections cannot be deleted by index, only wiped.** uci renumbers after
  a delete, so deleting =x.@type[0]=, =x.@type[1]=, ... hits empty slots once the list
  shifts, and stale options end up merged into what gets re-added (two of three
  =config host= entries collapsed into one, keeping the third's options). The fix is
  =while uci -q delete x.@type[0]; do :; done= — slot zero always names the current
  first section, so the loop empties the type and errors out of itself. No cap, no
  ordering subtlety. From openwrt-nix.
- **libuci hardcodes =/tmp/.uci=**, so =uci -c <copy>= does *not* isolate the staged
  delta -- the batch stays pending against the real configs. Cleaning that up by
  =uci revert= over every config is what =openwrt/preview.sh= does now instead: the
  delta is parked to =/tmp/.uci.nix-uci-park= and restored afterwards, because
  reverting it discarded whatever someone else had staged. Measured: a staged
  =dhcp= edit used to vanish across =just openwrt-diff= (1 staged line -> 0); now it
  survives. Showing a copy with a pending delta also prints deleted anonymous sections
  as bare =cfg<hex>= lines that the real config never contains, which is the other
  reason the delta gets cleared rather than ignored.
- **=uci batch= prints the generated name of every =add= section.** Capturing its
  stdout as config added nine phantom lines to every preview.
- **ash rejects =for x in <newline-separated words>;** the newline ends the command
  before =do= arrives. Anything derived from =sort -u= and interpolated into a remote
  =for= needs =tr '\n' ' '= — this one had been quietly breaking =openwrt-apply='s
  commit loop for a while.
- wipe-and-re-add moves a section to the *end* of the file, so both sides are
  sorted — otherwise every section the batch touches shows as changed. That sorting
  is blind to *named* sections being reordered (same content, different order), which
  is exactly what our own apply did to =wireless=; it is not blind to =firewall= rule
  order, because anonymous sections are indexed positionally, so swapping two rules
  changes =@rule[0].name= and the values differ. An explicit rule-sequence check is
  kept for that case and nothing else, so it is a guard, not the machinery.

=just openwrt-diff= ends with *no changes: the router already matches the declared
config*, which is the proof that the snapshot translation and the =wireless_key=
coming from =pass= are both right.

The flip side: anything **undeclared** is invisible to the diff, because uci reports
the whole file regardless of what Nix declares. That is the argument for declaring
the rest — the day LuCI writes a =firewall= rule we know nothing about, the diff
only catches it if =firewall= is declared. Until then =openwrt-facts= + =git diff=
is the drift check.

** Phase 3 — =network= + =firewall= (the lockout configs)

What is actually on the box (`openwrt/state/e8450/live/`):

| config    | options | sections | anonymous                                   |
|-----------|---------|----------|---------------------------------------------|
| =network=  | 21      | 6        | 1 =device= (=br-lan=, bridge over lan1-4)      |
| =firewall= | 94      | 13       | 1 =defaults=, 2 =zone=, 1 =forwarding=, 9 =rule= |

No config references another by anonymous index (`uci show | grep -E '^[a-z]+[^=]*=@[a-z]+\['`
is zero), so anonymous sections can be renamed to *named* sections here without
breaking anything. =fw4 check= reports the current config valid.

*Blockers before the first apply:*

1. **Closed — and my earlier reasoning was wrong.** I wrote that a sorted diff would
   report a reordered firewall as clean. It would not: =@rule[0].name= is positional,
   so reordering two rules changes the compared values. Verified by swapping two rules
   in the declaration — both the content diff and the rule-order note fired. Sorting is
   blind to *named* sections moving (the wireless case), where order carries no
   meaning. Kept anyway: =openwrt-diff= now compares content sorted and rule sequence
   separately, ~8 lines, and the check is demonstrated rather than assumed.
   One caveat found while wiring up =uci.raw=: =uci batch= does **not** exit nonzero
   when it rejects a command — a =reorder= of a section that does not exist prints
   nothing and returns 0 (measured). So a bad raw command shows up as "no changes",
   not as an error: use =raw= for things whose effect the diff can see, and never
   trust a clean run to prove a command took.
2. **Closed — anonymous types are wiped, not deleted.** =MAX_ANON_SECTIONS= is gone;
   =openwrt-diff=/=openwrt-apply= now run
   =while uci -q delete cfg.@type[0]; do :; done= before batching, from the =add= lines
   the batch already emits. That empties the type however many sections exist, and
   deleting slot [0] repeatedly is immune to uci renumbering (the bug in deleting by
   fixed index). Borrowed from openwrt-nix, whose architecture page spells out the
   idempotency strategy. The nine anonymous dhcp hosts sitting one below the old
   ceiling is why this came up now instead of at firewall time.

Named sections are no longer needed to dodge a ceiling — and for **rules they would
be wrong**: an attrset iterates alphabetically, so naming `rule 'Allow-Ping'` gives
the router alphabetical rule order, not the order declared. Proved on this box: our
own timezone apply rewrote `/etc/config/wireless` at 12:16 and its sections came out
alphabetical (`default_radio0` before `radio0`) rather than in declaration order.
Rule order is precedence, so declare rules as an **anonymous list**, where JSON array
order is preserved. Benign for `wireless`; fatal for `firewall`.

That reordering is also the proof that `openwrt/state/` still earns its keep: the sorted diff
could not see it, the snapshot's `git diff` could.

**What is left is the first real change** to `network` or `firewall`. That happened on
2026-10-11: a firewall rule added and then removed, applied with the rollback armed and
`firewall reload` running for real — so the mechanism is now demonstrated rather than
reasoned about, and it is what surfaced the reload bug in [[file:openwrt/justfile]]
(see *Phase 1/2 status*: applies had been committing without reloading since the
beginning).

What is *not* settled is the recovery path under that first change. The plan used to say
"confirm the console path, or be in the room". The console path was rehearsed and did
not work; see **Failsafe rehearsal** below. Practical translation: the watchdog is the
only protection we have measured, so one plane per run, and be physically present for
anything touching `network`.

*Safety, in the order that matters:*

- **The button failsafe is unavailable on this unit.** Rehearsed ~7× on 2026-10-11 and
  retried on 2026-10-16 with root SSH and a real UDP listener: neither the WPS button nor
  the UDP/4919 broadcast lands (details in *Failsafe rehearsal*). Serial is the option
  that also covers the device's known unbrick failure mode. =/tmp= is RAM: =sysupgrade
  -b= must be =scp='d off the router to count as a backup.
- first apply must be a no-op — translate exactly what is there, get an empty
  =openwrt-diff=, and change nothing. Risk starts with the first real change, not with
  declaring.
- preview with =fw4 check= against the staged copy (read-only, catches malformed
  config before it goes live).
- reload order: =network= first, give interfaces ~5s to come up, then =firewall=
  (=dnsmasq= for =dhcp=). One plane per run — never =network= + =firewall= + =wireless=
  together.
- rollback: **built** — =openwrt/rollback.sh=, armed by =openwrt-apply= before it
  commits and disarmed after, so a change that costs us the session undoes itself.
  The shape is openwrt-nix's, the details had to be ours:
  - arm = tar =/etc/config= to =/etc/rollback.tar= (flash, not =/tmp=), start
    =setsid sh rollback.sh= detached, =touch /tmp/rollback.armed=.
  - disarm = delete the marker. Not a signal: busybox has **no =nohup=**, and its
    =setsid= forks, so a recorded =$!= can point at a process that already exited.
    The script checks the marker after its sleep, so whoever disarms only has to be
    faster than 90 seconds.
  - fire = restore the tar over =/etc/config= and reload =network=, =firewall=,
    =dnsmasq=. That is the whole goal: a reachable router, not a verdict.
  - armed only when =changed= touches =network=/=wireless=/=firewall=, so ordinary
    applies pay nothing. =OPENWRT_FORCE_ROLLBACK=1 arms it anyway, for testing.
  - the decision to roll back is gated on whether ssh answers, **not** on the reload's
    exit status — a reload that drops the connection returns 255 on a perfectly good
    apply, and aborting there would roll back a change that was fine.
  Tested both branches: snapshot = SNAP-STATE, live = NEW-STATE, armed = SNAP-STATE
  again, disarmed = NEW-STATE stands.
  - *deliberately not built*: the boot-time =S15= hook. =/tmp= is RAM, so this watchdog
    dies with a reboot and cannot cover power loss mid-apply. On a box with 31 days of
    uptime, that is a far smaller risk than a bad rule, and =openwrt/state/e8450/live=
    is the manual path back for it. Add the hook if that ever stops being true.
- reloads are still synchronous. openwrt-nix detaches them
  (=( sleep 1; <reload>) >/dev/null 2>&1 &=) so ssh exits 0 before the interface
  bounces, which avoids exit 255 but also lets us disarm before the reload has taken
  effect — that is worse than an ugly exit code, because the disarm then proves
  nothing. What protects us is the watchdog plus the answering poll.
- =network reload= can drop the session and a bad =input= policy in =defaults= or a
  =zone= locks you out of the LAN, so apply one plane per run with someone in the room —
  the button failsafe is not a safety net we have confirmed.
- no =/etc/firewall.user= and no =include= lines here, so nothing outside the declared
  config gets merged in.

*** Failsafe rehearsal (2026-10-11)

The plan assumed the WPS button would put this E8450 into failsafe. It was rehearsed
against the box about seven times, with the laptop wired into the correct port, and the
router **never once entered failsafe**. Everything that the procedure depends on is
intact except the one thing that could not be observed.

Verified by reading the build, not the wiki:

- the window is =fs_failsafe_wait_timeout=4= in =/lib/preinit/00_preinit.conf=, and it
  opens about 6-10 s after the =reboot= command — the kernel banner logs in the same
  second the command runs. The LAN does not answer for ~40 s, which is why timing this
  from the laptop is the hard part, and why an observer that assumes the router is down
  at +0 s reports a false negative in under a second.
- interface selection falls through to the default branch of
  =/lib/preinit/05_set_preinit_iface= — =ip link set eth0 up; ifname=lan1= — so failsafe
  answers on **LAN1 only**. Confirmed by pushing traffic down the cable and reading
  =/sys/class/net/lanN/statistics/rx_bytes=: lan1 counted it, lan4 counted zero.
- pressing WPS arrives as =ACTION=pressed BUTTON=wps TYPE=<empty>=, and the handler is
  =[ "${TYPE}" = "switch" ] || echo ${BUTTON} > /tmp/failsafe_button=, so an actual
  button *would* write the flag. After boot the same press goes to
  =/etc/rc.button/wps=, which starts with =exit 5= — a real no-op.
- =gpio_button_hotplug= loads at 3.7 s of kernel time from =/etc/modules-boot.d=, so
  the driver is not late, and =/sbin/init= does reference =/etc/hotplug-preinit.json=,
  so the preinit routing is wired rather than merely shipped.
- squashfs =ro= root with overlay on =/dev/ubi0_7=, so the prerequisite holds.

Two measurement traps, both of which produced a wrong conclusion here before the right
one:

- the only witness is =/tmp/failsafe_button=, and it is present only if the handler ran
  during that boot. Nothing else in the running system records it.
- instrumenting =/etc/rc.button/*= to log presses cannot see the window: during preinit
  =/etc= comes from squashfs, so an overlay edit is invisible until after
  =mount_root= — i.e. after the window has closed. Logging =at=$(cut -d. -f1
  /proc/uptime)= makes it worse, because uptime resets every boot, so those lines cannot
  be attributed to any particular boot. A per-boot witness has to live in =tmpfs=.

So: failsafe is *plausible*, not broken, and not yet proven. The earlier
"instrumentless" conclusion was wrong on two counts, both from the OpenWrt wiki:

- **failsafe is reachable over SSH.** It starts at =192.168.1.1= with DHCP and wireless
  off, so no serial console is needed to *use* it — a static =192.168.1.10= on the laptop
  and =ssh -oRSAMinSize=1024 root@192.168.1.1= is enough, then =mount_root=. Serial is
  only needed to watch preinit or to unbrick the bootloader, not to recover config.
- **there *should* be a timing oracle.** During the 4s window (24.10+) the box
  broadcasts =Please press button now to enter failsafe= to =192.168.1.255:4919=.
  =tcpdump -Ani <lan> port 4919 and udp= makes the window visible from the laptop, so
  the press no longer has to be guessed from LED blink patterns. *Retried 2026-10-16
  with a root SSH login and an unprivileged UDP listener: the broadcast exists but never
  reaches the wire — =lan1='s link is down for the whole window. See the dated
  subsection below.*

To settle it (no cable): LAN1 wired, laptop static at =192.168.1.10=, =tcpdump= on the
UDP/4919 broadcast, reboot the router, press WPS the moment the packet appears, then
=ssh= to =192.168.1.1= (clear the stale known_hosts entry first — the failsafe host key
differs), =mount_root=, fix, =reboot=. *This paragraph is the 2026-10-16 attempt, and it
does not work on this unit* — the broadcast is dropped before it reaches the wire and the
button never lands. =failsafe=1= on the kernel cmdline (more =fw_setenv= on a board with
the OKD history) and serial are the fallbacks; serial also covers the unbrick case.

Until one of those is done, treat the watchdog as the only measured protection: one
plane per apply, and be present.

**** 2026-10-16: retried with root SSH + a real listener; both routes fail

The cable-free route above was retried properly, with none of the earlier blind spots:
root SSH from asche to the e8450, asche wired to the physical **lan1** port, its NixOS
firewall opened for UDP/4919, and a real UDP listener (not =tcpdump=) bound on 4919.
It failed, for a reason that also explains the button's seven misses.

- **The timing oracle cannot work.** Preinit really does broadcast "Please press button
  now to enter failsafe" to =192.168.1.255:4919= on raw =lan1=, but =lan1='s PHY link is
  still down for the whole 4s window and only returns afterwards:

  #+begin_example
  05:39:31 carrier=0   # reboot
  05:39:37 carrier=0   # ← the 4s window; frames are dropped here
  05:39:42 carrier=1   # link returns, window already closed
  #+end_example

  A manual =netmsg 192.168.1.255= arrives fine once the link is up, which is why the
  probe-loop test looked promising while the actual boot never delivered.

- **The WPS button still does not enter failsafe.** It is genuinely wired:
  =/proc/device-tree/gpio-keys/wps= has =gpios= (12 B) and =linux,code= (4 B),
  =gpio_button_hotplug= loads at 3.7 s, and =/etc/hotplug-preinit.json= routes
  ~SUBSYSTEM=button~ to =/etc/rc.button/failsafe= (which writes =/tmp/failsafe_button=).
  A single press, and then one press a second for ~20 s across the window, both booted
  normally (=hostname OpenWrt=, no =/tmp/failsafe=).

So the no-cable route is closed on this unit. The remaining ways are serial (also the
device's only real unbrick path) and =failsafe=1= via =fw_setenv= (rejected here: a bad
=bootargs= on a box with no serial needs TFTP recovery). Treat failsafe as
*unavailable*, and the watchdog as the only measured protection -- until the
2026-10-17 re-read and retry below says otherwise.

**** 2026-10-17: re-read on the live box -- the wire route is a lost race, not a dead port

Every failsafe file was re-read on the unit (25.12.5, deploy key, read-only), and the
2026-10-16 conclusion needs one correction: preinit *does* bring the failsafe port up.
The wire failure is a carrier race, and the direct cable loses it by a second or two:

- =10_indicate_preinit=::=preinit_ip= runs before the window and does
  ~ip link set dev lan1 up~ plus =192.168.1.1/24= on it; =30_failsafe_wait= then
  broadcasts ~netmsg~ once a second for ~fs_failsafe_wait_timeout=4~. Nothing on the
  disk is broken; upstream master is the same.
- =init: - preinit -= logs at 3.8 s kernel time on this box, so the window sits at
  ~kernel 4-8 s (wall +5-10 s after =reboot=) -- the 1/s press schedule *did* cover it,
  which makes the button's silence unexplained and, with preinit =/etc= being squashfs,
  unobservable without serial.
- The carrier samples (link back only ~+11 s) are the MT7531 PHY and the Mac's USB-C
  NIC renegotiating from cold, ~4-6 s. The four broadcasts end right around when
  carrier first appears, so a direct asche-->lan1 cable gets zero packets without the
  script being wrong. The margin varies per boot and per link partner, so the race can
  be won by changing the partner (see the protocol).
- Two new facts for any retry: this device tree has *no* function LEDs, so =/etc/diag.sh=
  shows nothing in failsafe -- there is no LED oracle. And the recessed *reset* button on
  a booted box *reboots it on a short tap and factory-resets at >=5 s hold*
  (=/etc/rc.button/reset=) -- never tap reset blind; WPS is the only safe button
  (=rc.button/wps= =exit 5=).
- Success oracle without serial: entering failsafe sets the hostname to
  =OpenWrt-failsafe= (=10_indicate_failsafe=), and the failsafe boot runs a default
  =br-lan= 192.168.1.1 with DHCP and ssh on the lan ports. =ssh root@192.168.1.1=
  answering with that banner is proof; =mount_root= then reaches the real overlay.

Retry protocol (no unboxing, ~5 min per boot, house LAN down for ~1 min per boot):

1. Put a *switch* between asche and physical =lan1= -- the house switch or any dumb
   switch. asche's own carrier then survives the reboot, and the only renegotiation
   left is switch<->lan1, which finishes well inside the window. This is the one
   variable the 2026-10-16 run lacked.
2. asche: static =192.168.1.10/24= (or keep its lease), firewall open for UDP/4919, run
   =python3 openwrt/failsafe-listen.py= (add =--speak= if the screen is out of sight).
   Sanity-check the receive path first: with the router up,
   ~ssh root@192.168.1.1 netmsg 192.168.1.255 test~ must print in the listener.
3. =ssh root@192.168.1.1 reboot=. From wall +4 s, tap WPS about twice a second until
   +12 s; when the listener prints, tap once more. Taps only -- never reset.
4. If the router answers: =ssh root@192.168.1.1= and read the banner. =OpenWrt-failsafe=
   -- failsafe reached, =mount_root=, fix, =reboot=. Normal banner and no
   =/tmp/failsafe= -- do boot 2: repeat once *holding* WPS down from +3 s to +12 s
   (a hold guarantees a press event inside the window if dispatch works at all).
5. Both boots fail -- the finding stands as before, failsafe is unavailable on this
   build without serial, and the permanent no-unbox fix is one line at the next
   sysupgrade: an imagebuilder image with ~fs_failsafe_wait_timeout=10~ in
   =00_preinit.conf= (Phase 4 material). The window being shorter than PHY bring-up
   on DSA boards is worth an upstream ticket either way.

**Boot 1 result (same day): inconclusive -- the box hung; and the rescue story changed for the better.**
The run followed the protocol (switch between asche and lan1, listener armed,
receive path proven with a manual netmsg, reboot fired at 14:20:16, WPS tapped).
The router never came back: ~3.5 minutes dark, recovered by a manual power cycle.
The listener received zero packets the whole time with a live receive path, so
preinit never ran and no failsafe window ever opened -- the taps were never given
a chance; the soft reboot itself hung.

**Not OKD.** Reading =/dev/mtd0= afterwards shows the bootloader already runs the
fixed TF-A: =v2.10.0 (release):OpenWrt v2024.01.17~bacca82a-3= -- exactly the
build the device page ships as the OKD fix. So the hang was a one-off, unexplained
boot failure (power cycle recovered it, first occurrence observed), not the known
disease, and flashing a newer =bl2= buys nothing.

**The rescue path that actually exists: the installer's recovery system.** This box
has a =recovery= UBI volume (and =boot_backup= with the vendor bootchain, both
confirmed present), and two documented ways into it, neither needing serial:

- *PSTORE trigger, keeps configuration*: from a running OpenWrt,
  ~echo c > /proc/sysrq-trigger~ panics the box; U-Boot sees the ramoops record
  and boots the recovery system, which serves ssh/http/tftp for restore or
  upgrade. ~rm /sys/fs/pstore/*~ and reboot returns to production. Verified armed
  on this box: ~kernel.sysrq=1~, =/sys/fs/pstore= empty, recovery volume present.
- *Reset at power-on, wipes configuration*: hold reset while powering up, release
  when the power LED turns orange. Last resort for a box that cannot boot; the
  declarative config makes the wipe survivable.

This covers the swap's real risk class (boots fine, config locks us out) better
than failsafe ever could -- it keeps the config and needs no button, no window,
no carrier race. It was found in the installer README, hiding in plain sight since
the original install.

**What is left of the failsafe track:** the button's silence stays unexplained and
unobservable without serial; the wire oracle stays a carrier race. Neither is worth
more blind reboots now that recovery mode is the safety net of record. The one-line
~fs_failsafe_wait_timeout=10~ imagebuilder fix remains queued as Phase 4 material,
to ride along the next sysupgrade that happens anyway -- not as a standalone flash.
The rehearsal of the PSTORE path is the runbook immediately below.

**** PSTORE recovery rehearsal (runbook, not yet run)

Goal: make the rescue path *measured* the way the watchdog is, not just documented.
Preconditions all verified on the box 2026-10-17: =kernel.sysrq=1=, ramoops backend
registered at boot (~pstore: Registered ramoops as persistent store backend=,
0x10000@0x42ff0000), and the =recovery= UBI volume begins with a valid
=ARM64 OpenWrt FIT= image. Plan for ~5-8 min of house downtime (WiFi + internet down
the whole time; the one unexplained boot hang earlier today puts a small chance on
needing a power cycle, so stay near the box).

Pre-flight (2 min):

1. Pull a full backup off the box (the rehearsal keeps config, but that is the
   claim being tested):
   #+begin_src bash
   ts=$(date +%Y%m%dT%H%M%S)
   ssh -i ~/.ssh/id_deploy root@192.168.1.1 'sysupgrade -b /tmp/pre-pstore.tar.gz'
   ssh -i ~/.ssh/id_deploy root@192.168.1.1 'cat /tmp/pre-pstore.tar.gz' \
     > openwrt/state/backups/e8450-pre-pstore-$ts.tar.gz
   #+end_src
2. Clear the known_hosts entry now -- recovery has its own host key, and it flips
   again on the way back: ~ssh-keygen -R 192.168.1.1~.

The run:

3. Fire the deliberate panic from a running system (the session dies instantly --
   that is the crash, not an error):
   #+begin_src bash
   ssh -i ~/.ssh/id_deploy root@192.168.1.1 'sync; echo c > /proc/sysrq-trigger'
   #+end_src
4. U-Boot sees the ramoops record and boots the =recovery= volume instead of =fit=.
   Expect asche (wired via the switch to lan1) to get a DHCP lease from 192.168.1.1
   within ~1-3 min: watch ~ip -br addr show enp0s13f0u3c2~. WiFi stays down --
   recovery has no wireless.
   - No lease after ~3 min: set a static =192.168.1.10/24= on the wired NIC and try
     ssh/http anyway; if still nothing after another minute, power-cycle -- the
     pstore record persists, so it boots recovery again.
5. Enter recovery and confirm it is what it claims: ~ssh -i ~/.ssh/id_deploy
   root@192.168.1.1~ answers, and =cat /proc/cmdline= does *not* show
   =ubi.block=0,fit= (that is the production boot; recovery boots its own FIT).
   The http://192.168.1.1 firmware-upload page should also answer.
6. Optional proof the config is intact: ~mkdir -p /tmp/r && mount -t ubifs -o ro
   ubi0:rootfs_data /tmp/r && ls /tmp/r/upper/etc/config~ -- read-only, unmount
   after.
7. Clear the panic record -- the switch back to production. Skipping this makes
   *every* subsequent boot re-enter recovery:
   #+begin_src bash
   rm /sys/fs/pstore/*
   #+end_src
8. ~reboot~ -- production boot (~1 min, WiFi returns).

Post-checks (the part that makes it measured):

9. =ssh root@192.168.1.1= answers with the *production* host key again (flip
   known_hosts back), =uptime= is fresh, ~just openwrt-diff~ is clean, asche's
   lease =192.168.1.200= is back, internet is up, and =ls /sys/fs/pstore= is
   empty on the production side too.

Abort paths:

- Hang on the way in (the failure mode seen earlier today): power-cycle; the record
  persists, recovery is the destination again -- keep trying.
- Want out any time after step 7: that *was* the way out.
- Recovery volume unbootable: the reset-at-power-on entry lands in the same volume,
  so it does not help; that is the one tail risk of this rehearsal and its only
  exit is serial. The pre-flight volume check makes this unlikely, not impossible.

Decision 2026-10-17: the swap does not gate on this rehearsal. The e8450 half of
the swap is a uci apply -- config-plane only, it cannot make the box unbootable
-- and the failure class it can create is what the *tested* watchdog plus the
pulled pre-apply backup already cover. Recovery mode stays the armed deep
fallback (preconditions verified read-only today). The bet in skipping: if the
boot-plane class hits mid-swap anyway, the no-unbox rescue is unexercised and
the last resort is opening the case for serial. Run the rehearsal at any calm
moment later; it is insurance, not a gate.

** Phase 4 — deferred, do not build yet

- =opkg= package management (declarative install/remove). Needed when the
  running package set diverges from declared; a ~pkglist= diff is enough then.
- =sysupgrade= flow + =at=-based remote rollback (the upstream Justfile has the
  =wget= -> =sysupgrade= -> =just apply= shape, worth stealing once versions matter).
- imagebuilding (=astro/nix-openwrt-imagebuilder=) instead of =opkg=: reproducible
  images and no package drift, but you take on a full cross toolchain and a
  much heavier flash cycle. Only worth it if we end up with 2+ routers.
- =/etc/crontabs/root=, =/etc/sysctl.conf=, =/etc/dropbear/authorized_keys= — these are
  file-level, not uci. Handle as plain =rsync=-deployed files in the same
  =justfile= (upstream does =authorized_keys= exactly this way in its =apply= target).

* Alternatives considered

- [[https://github.com/lonerOrz/openwrt-nix][lonerOrz/openwrt-nix (nuci)]] — same design as upstream, plus =nuci diff=, =nuci deploy=
  with a 60s watchdog and imagebuilder support. Actively maintained (last push
  Aug 2026). The "real project" upstream said it would switch to. If we want
  watchdog rollback on day one, consume this instead of vendoring.
  Recommendation: vendor the small upstream now (we control the ~200 lines),
  steal what nuci does better. Three things taken: the wipe-first idempotency
  strategy for anonymous sections (better than upstream's delete loop, and the
  reason =MAX_ANON_SECTIONS= is gone), the =rawUci= escape hatch as =uci.raw=, and its
  rollback shape — detached reload plus a 60s in-session watchdog and a =S15=
  boot-time restore, still to build in phase 3.

  Decided against switching wholesale on 2026-10-10, on the repo rather than the
  docs: 9782 lines against our 464, the =uci.settings=/=_type= schema is already identical
  so nothing is gained in expressiveness, their generator emits
  =touch; uci -q batch; commit= per config (auto-commit guarded by the watchdog, where our
  flow previews and confirms first), and secrets assume sops while ours come from
  =pass=. Revisit for declarative packages (=uci.packages=, =packageSources=), or if we
  want imagebuilder firmware, or when we hit a bug they have fixed.
- ~nix-openwrt-imagebuilder~ — reproducible images, heavy. Deferred.
- ~openwrt-configuration~-style full image rebuild — same tradeoff, no.
- =nix-on-derbarou= / =nixos-anywhere= style "nixify the router" — no. OpenWrt is
  the platform; we want its =uci=, not NixOS.
