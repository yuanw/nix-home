* TL;DR

Settle [[file:mono-gateway-cutover.org][cutover decision 7]] (adblocking). dnsmasq stays the LAN's front door;
AdGuard Home joins behind it as a *loopback-only* filter hop, and dnsmasq gets one
forwarding line pointing at it.

| Piece | Change |
|-------+--------|
| dnsmasq | +1 line: ~server = [ "/#/127.0.0.1#5354" ]~ |
| AdGuard Home | ~services.adguardhome~ (upstream module), bound to =127.0.0.1= |
| Firewall | nothing. Loopback binds cannot be reached from eth2, so no new input rule |
| DHCP | nothing. Clients already get DNS =192.168.1.1= via option 6 |
| New files | none |
| New dependencies | none beyond ~pkgs.adguardhome~, which rides in the closure the deploy copies |

The whole change is ~25 lines in =hosts/mono-gateway/default.nix=. It is one
generation wide from rollback, which is what makes it safe to run on a live router.

Blocking is net-new — the e8450 never filtered (see *The premise of decision 7*
below). The thing the cutover *did* leave behind is upstream privacy: the AP sent
DoH, the board sends plaintext UDP to the ISP. That is decision 1, and it is the
more important half of this plan.

** The premise of decision 7 does not hold: the e8450 never filtered

*AdGuard Home is installed on the e8450 and is not in any DNS path* (confirmed
2026-10-17; worth a re-check if this doc outlives the AP). The cutover's
"What exists today" table says dnsmasq forwards to AdGuardHome — it does not. The
live dhcp config is ~server = 127.0.0.1#5053 / 127.0.0.1#5054~, which is
https-dns-proxy doing Cloudflare DoH, and =openwrt/routers/e8450.nix= declares
only the UCI stub (workdir + config_file), no filters and no upstream. Nothing
routes to an AGH listen port.

That changes the shape of this work:

- *Decision 7 is net-new, not a parity requirement.* No house behaviour depends
  on AGH today, so nothing here is at risk of being lost in the migration, and
  there is no "the swap broke adblocking" incident to recover from. Declare
  =filters = [ ]= and the change is a no-op for every client.
- *Nothing to migrate.* =/etc/adguardhome/adguardhome.yaml= on the AP is the
  default/no-rule config, so there is no state to copy and no rules to diff
  against. The lists are a fresh choice.
- *The parity item is privacy, not blocking, and the board is behind.* The AP
  resolved over Cloudflare DoH and =force_dns=1= redirected everything into it;
  the board forwards plaintext UDP to whatever the ISP hands out in
  ~/etc/resolv.conf~. That is the property actually lost at the swap — which is
  why decision 1 below is the more important half of this plan, not the filters.

* Design

** The hop order

Clients → =dnsmasq 192.168.1.1:53= → =AGH 127.0.0.1:5354= → upstream

dnsmasq keeps answering everything it answers today: leases and their =.lan=
names (=dgx-spark.lan=, needed by misfit's caddy vhosts), the two static leases,
~address = /.yuanw.me/192.168.1.190~, =local=/lan/=, =bogus-priv=. Only queries
it does not already own an answer for move on to AGH. AGH is therefore *purely
additive*: if it dies, resolution still works, just unfiltered.

** Why not put AGH on =:53= instead

The alternative is AGH owning port 53 and dnsmasq dropping to =port = 0= (DHCP
only). Rejected:

- Everything dnsmasq serves from leases/statics/=address=/ has to be rebuilt
  inside AGH (=local_dns_hosts= + rewrites), and a name built off a lease cannot
  be pinned there — that is the exact =dgx-spark.lan= problem the cutover already
  had to solve once.
- It changes two things at once on a router one day into service, for a feature
  with no measured need yet.
- It costs the loopback property, which is what makes the later VPN/unbound work
  cheap (see *Later additions*).

One line against a rewrite. Take the line.

** Two details that are not obvious from the module docs

- *Non-53 port on purpose.* dnsmasq binds =br-lan= only (=bind-interfaces=), so
  =127.0.0.1:53= would be free. Using =5354= anyway keeps AGH from ever racing
  dnsmasq for =:53= across a restart, which is the failure mode that would look
  like "the house resolves nothing".
- *The web UI goes on loopback too.* =host = 127.0.0.1= and =port = 3000= are
  options on the service, *not* keys in =settings= — current nixpkgs asserts
  =settings.bind_host= away as "superseded by =services.adguardhome.host=", and
  since =host= defaults to =0.0.0.0=, setting it explicitly *is* the exposure
  decision. Reached over ssh:

  #+begin_src bash
  ssh -N -L 3000:127.0.0.1:3000 root@192.168.1.1     # then http://localhost:3000
  #+end_src

  No =openFirewall =  true= (that is a global =tcp dport 3000=, exactly the class
  of unscoped rule that already put ssh on the WAN side), no =br-lan= rule, no
  =host = 192.168.1.1= coupling the service to an address that a future
  generation might move.

  That is what 1.4 built and confirmed: =host=/=port= are mapped onto
  =http.address = 127.0.0.1:3000= at this schema version, with no =bind_host= key
  anywhere.

  If the tunnel is too much ceremony, the LAN-click version is =host =
  "192.168.1.1"= + =interfaces."br-lan".allowedTCPPorts = [ 3000 ]= and a vhost on
  misfit's caddy next to =openwrt.yuanw.me=
  (~reverse_proxy http://192.168.1.1:3000~). That trades the loopback bound for
  convenience, and then the =auth.users= hash above is *required*, not optional —
  a hostname on =*.yuanw.me= is a wider reach than =127.0.0.1=.

** The config

The block itself is in [*1.2 The edit*](#the-edit--two-places-in-hostsmono-gatewaydefaulnix).
~services.adguardhome~ is an upstream NixOS module: import nothing, add no module
file (the in-repo fork is obsolete — see *Decisions still open*). =mutableSettings=
defaults to =true=, so UI-side changes survive restarts while the keys we declare
win at every start.

Deliberately *not* copied from =modules/adguard.nix= (deleted, along with the
fork): that config's
~cache_size = 536870912~ is 512 MB of cache on a box whose RAM budget is not
known here, its ~upstream_dns = [ "127.0.0.1:5335" ]~ points at an unbound that
is not enabled, and its wg/iptables/age pieces belong to the retired AWS box.

#+begin_src nix

  # dnsmasq stays the front door; AGH is a loopback filter hop behind it, so
  # there is no firewall rule to add and nothing for clients to configure.
  services.adguardhome = {
    enable = true;
    openFirewall = false;
    host = "127.0.0.1"; port = 3000;   # service options, NOT settings.bind_host
    settings = {
      dns = {
        bind_hosts = [ "127.0.0.1" ]; port = 5354;   # NOT bind_port, see below
        upstream_dns  = [ "94.140.14.14" "1.1.1.1" ];   # decision 1
        bootstrap_dns = [ "1.1.1.1" ];
        filtering_enabled = true;
        filters = [ ];                 # nothing to migrate; pick lists
        cache_size = 4194304; cache_ttl_min = 300; cache_optimistic = true;
        querylog_enabled = true; querylog_file_enabled = true;
      };
      # decision 2: close the UI if loopback + ssh stops being enough
      # auth.users = [ { name = "yuan"; password = "<bcrypt: htpasswd -B -n yuan>"; } ];
    };
  };
#+end_src

Two rules: no =bind_host= / =bind_port= keys inside =settings= (the module asserts

*** 1.4 Read what the build generated — the actual point of Phase 1

Both configs are store paths referenced by the unit files, exactly the technique
the cutover used to read =dnsmasq.conf=. The Phase-1 run needed two corrections to
that recipe:

- the closure is in dgx-spark's store, so every read here is an ~ssh~;
- =AdGuardHome.yaml= is *not* referenced by =adguardhome.service= — with
  =mutableSettings = true= (the default) the unit's =ExecStartPre= script is what

#+begin_src bash

*** Phase 2 as run — 2026-10-17

Gen 20 → 21 → 22. The first activation exposed a bug Phase 1's read could not
see: the generated yaml carried =dns.bind_port: 5354=, but the 0.107.71 binary
reads =dns.port= and ignores =bind_port= — so AGH bound =127.0.0.1:53=, collided
with dnsmasq, and crash-looped until the restart timer. =server=/#/…= was live
by then, but external names still resolved: dnsmasq falls back to its global
(resolv.conf) nameservers when 5354 refuses, so the house never lost DNS, only
would have lost the hop silently. The fix is one key — =dns.port = 5354= — built
and activated as gen 22; =bind_port= is not re-declared since it is ignored.

| Proof (2.2/2.3) | Result |
|-----------------+--------|
| =adguardhome= | active, =NRestarts=0; =udp+tcp 127.0.0.1:5354= =AdGuardHome=, =tcp 127.0.0.1:3000= only, =udp 192.168.1.1:53= still =dnsmasq= |
| client: =example.com= / =.lan= / =.yuanw.me= / WAN | all first try: addresses, .185, .190, =71.17.19.228= |
| the forward is all-or-nothing, not round-robin | 10 unique names from a client, 10/10 in AGH's =/control/querylog= — no leak to the ISP resolvers |
| rollback half of 2.4 | *not run* — gen 21 → 22 exercised the reverse direction only |

Two facts the runbook's own commands would have missed: the board has no =dig=
(the proof commands need =host=, or run =dig= from a client), and
=/control/querylog_search= is 404 in 0.107.71 — the ring is
=/control/querylog?limit=100=, and it flushes to
=/var/lib/AdGuardHome/data/querylog.json= once the 1000-entry memory ring
wraps, so the file appearing is normal but not immediate.

*** 2.6 What Phase 2 must NOT be followed by

No rule lists are declared (=filters = [ ]=), so the natural next move is to add
them in the UI. *Before doing that*, read this: =mutableSettings = true= merges
declarative config *over* the state file with =yaml-merge=, and =yaml-merge=
replaces lists rather than unioning them. Verified on dgx-spark with the
=yaml-merge= this closure uses (the store path is the same derivation the
=adguardhome= unit runs):

#+begin_src bash
Y=/nix/store/l185hixf1zn5bx04frv2kcwrfqf4c3s5-yaml-merge-0-unstable-2022-01-12/bin/yaml-merge
# state file with a UI-added list, then the declarative config
$Y <(printf 'dns:\n  filters:\n  - {enabled: true, id: 1, url: https://a.txt}\n  cache_size: 4194304\n') \
   <(printf 'dns:\n  filters: []\n')
# -> dns: {cache_size: 4194304, filters: []}        the UI's list is gone

# control: declare nothing about filters and the list survives
$Y <(printf 'dns:\n  filters:\n  - {enabled: true, id: 1, url: https://a.txt}\n  cache_size: 4194304\n') \
   <(printf 'dns:\n  cache_ttl_min: 300\n')
# -> dns: {cache_size: 4194304, cache_ttl_min: 300, filters: [{…https://a.txt}]}
#+end_src

=dnsmasq.conf= is unaffected by this, so nothing in 2.0–2.5 changes — but every
=switch-to-configuration= would silently wipe whatever the UI added. Pick one
before adding lists:

1. drop =filters = [ ]= from =hosts/mono-gateway/default.nix= and manage lists in
   the UI, where they then persist; or
2. declare the lists there, which keeps the whole filter set in a diff and is
   the only variant that survives a re-flash.

Option 2 is what this file's own conventions point to. It is a Phase 3 change,
not a Phase 2 one.

Record in the doc and the commit: new generation (=21= unless something else

** Phase 3 in detail — rule lists, declared in nix

Everything so far is mechanism: the hop works, nothing is blocked. Phase 3 is the
one line that makes the plan's title true, and it is the shortest change in the
whole rollout — but it is the first step that can *break a house service*, so it
is staged.

Two things to start settled:

- *Phase 3 does not wait on decision 4.* The fallback only fires when AGH is
  *unreachable*: dnsmasq tries 5354, gets refused, asks the ISP. A *blocked*
  answer is an answer — NXDOMAIN comes back through dnsmasq and nothing else is
  consulted. So the lists work as well today as they would after =no-resolv =
  true=; what changes later is only what happens when AGH is down.
- *Declare them, do not click them.* =yaml-merge= replaces lists, so a list added
  in the UI is wiped by the next rebuild (*2.6*, verified). The house convention
  is that router policy is reviewable in git, and this is policy.

*** 3.1 The config

In =hosts/mono-gateway/default.nix=, replace =filters = [ ]= with the list set.
Ids are declared so a later UI-add cannot collide with one, and =name= is set
because it is what the query log shows.

        # lists, so anything added in the UI would vanish on the next rebuild.
        # These ids are ours; don't let the UI reuse them.
        filters = [
          {
            enabled = true;
            id = 1;

*** 3.4 The first day, and what to do when a real service breaks

A day of real traffic before widening anything — one browser tells you nothing
about the TV, and the query log is the only evidence available.

#+begin_src bash
# from the board, newest first (the ring is ?limit=N, the search endpoint is 404)
ssh root@192.168.1.1 "curl -s 'localhost:3000/control/querylog?limit=100&response_type=json' | tail -c 800"
# or the UI over the tunnel: ssh -N -f -L 3000:127.0.0.1:3000 root@192.168.1.1
#+end_src

This is where =REJECTED= entries for something like a push domain or a login node
turn up before anyone says "the internet is slow".

When something real breaks, three levers, fastest first:

1. **Pause filtering.** The UI's protection switch, or now:
   #+begin_src bash
   ssh root@192.168.1.1 systemctl stop adguardhome
   #+end_src
   The house is back on unfiltered DNS in seconds because of dnsmasq's fallback
   (*2.4*). Both forms are temporary — the next rebuild reasserts the declaration.
   This is decision 4 being *useful*, and it is why 4 can stay open during Phase 3.
2. **Allowlist the domain properly.** Where user rules actually live is *not
   verified*: the UI writes them under =/var/lib/AdGuardHome/data/filters/= rather
   than into the yaml, so whether one survives a rebuild is an open question.
   Discover it the way everything else here has been discovered — add it in the UI
   once, then look:
   #+begin_src bash
   ssh root@192.168.1.1 'grep -rn "<the-domain>" /var/lib/AdGuardHome/data/ /var/lib/AdGuardHome/AdGuardHome.yaml | head'
   #+end_src
   Whatever key or file that turns up is what gets declared. Until then lever (1)
   is the fix, and never rebuild onto an allowlist whose persistence is unknown.
3. **Drop the list.** Revert one entry in =filters= and redeploy. With two lists
   this is a real option, which is another reason 3.1 starts at two.

*** 3.5 Widen, or stop

After the day: clean log, both tables pass → add a third list declaratively and
repeat 3.2-3.4. Anything real blocked → fix per 3.4 and do not widen until it has
been quiet. There is no goal that says how many lists the house needs; the
mechanism is already live, and "two lists, boring, no incidents" is a legitimate
place for this plan to end. If the log never fills with anything worth blocking,
that is the answer, not a failure to have done more.

Record afterwards: rule counts from =journalctl=, =MemoryCurrent=, both tables run
from a client (not the board), whether lever (1) was needed by anyone in the
house, and the generation. Then decisions 4 and 1 — closing the fallback and
moving upstream to DoH — are what make the filtering mean something, and they are
deliberately not Phase 3.

** Phase 3 checks

Only meaningful once rule lists exist — see *Phase 3 in detail*. What follows is
the Phase 2 gate, which stays useful as a smoke test after every deploy.

#+begin_src bash
# from a house client
dig +short example.com @192.168.1.1           # want: an address, fast
dig +short doubleclick.net @192.168.1.1       # want: nothing (blocked, once lists exist)
dig +short dgx-spark.lan @192.168.1.1         # want: 192.168.1.185  -- dnsmasq local wins
nslookup -type=A doubleclick.net 127.0.0.1    # want: no answer
#+end_src

The third line is the regression check that matters: dnsmasq's own data must
still be answered *without* reaching AGH, so the =.lan= names and =*.yuanw.me=
must be unaffected by the new forward.

* Decisions still open

| # | Question | Options |
|---+----------+---------|
| 1 | Upstream | public IPs (works today, plaintext) vs DoH/DoT — the half the cutover actually lost, and what survives a later VPN client |
| 2 | Admin credentials | loopback + ssh, unauthenticated (default: nothing in git, nothing to rotate) vs declarative =settings.auth.users= with a bcrypt hash |
| 3 | Bypass | a client hardcoding 8.8.8.8 skips the board entirely. The e8450 closed that with =force_dns=1= (a real redirect). Close it later with a =br-lan= nft redirect to =.1:53= |
| 4 | Advisory or authoritative | dnsmasq's ~/etc/resolv.conf~ fallback means AGH is advisory: 5354 refuses → the ISP resolvers answer. Keep it (dead AGH ≠ outage) or close it with =no-resolv= (AGH becomes the only path — filtering is guaranteed, and an AGH outage now means no resolution) |

Decisions 1, 3 and 4 are one decision wearing three hats. DoH on AGH alone does
not make the house's DNS private while dnsmasq still has a plaintext fallback,
and an nft redirect is only meaningful once that fallback is gone — so the order
that actually moves things is **4, then 1, then 3**. Doing 1 first buys encrypted
upstreams on half the traffic and a false sense of having fixed it.

*Two corrections from the Phase-3 run.* First, that ordering assumed a leak; the
leak was measured and is not there. 12/12 unique cache-missed names from a client
reached AGH and its ~/etc/resolv.conf~ resolvers answered none of them, so
"dnsmasq is still leaking to the ISP" is only true when =127.0.0.1#5354= *refuses*
— the gen-21 case. Decision 4 is therefore about guaranteeing filtering during an
AGH outage, not about stopping a leak that is happening. Second, decision 1 is
already half-made, by someone else: see the next section.

** Decision 1 has been made for you, by =94.140.14.14=

=94.140.14.14= is not a plain recursive resolver — it is AdGuard's own *filtering*
service. Measured 2026-10-17, before this file had any filters declared:

#+begin_src bash
dig +short doubleclick.net     @94.140.14.14   # -> 0.0.0.0
dig +short google-analytics.com @94.140.14.14  # -> 0.0.0.0
dig +short google-analytics.com @1.1.1.1       # -> 142.250.73.68 (real)
#+end_src

So three things this plan said need restating:

- *The house was never unfiltered.* It has been ad-blocked server-side by AdGuard's
  DNS since decision 1 shipped, silently, with no declarative trace and no rule
  list anyone chose. Phase 3 is *less* mystery and *more* determinism than what it
  replaces, not more blocking.
- *=upstream_dns= currently pairs a blocking resolver with an unfiltered one under
  =load_balance= (confirmed in the =journalctl= startup line). For any name not in
  our own list, the answer depends on which one answers first. That is an
  accidental policy, not a design.
- *The DoH question should be asked against a non-blocking resolver.* Swapping to
  =https://dns.cloudflare.com/dns-query= (or quad9/nextdns, unfiltered) is the
  version of decision 1 that keeps the semantics and drops the plaintext; keeping
  an AdGuard DoH endpoint would just relocate the same undeclared server-side
  filtering into TLS.

For 4 the cheap half is: stop feeding dnsmasq the ISP's resolvers and give it
nothing but AGH (=no-resolv = true= in the same =settings= block that already
carries =bogus-priv= and =bind-interfaces=), then confirm from a client that a
name resolves only via AGH's upstreams. The risk of that switch is in *Known
limits*: it converts an AGH failure into an internet outage for the house.

Decision 2 is settled by the upstream module: the fork is obsolete, not just
stale.

- It exists because 2019-era AGH ran a setup wizard and kept its credential in
  =user.json=. Upstream's =preStart= now writes the generated yaml before the
  first start (=installFresh=), so *the wizard skip is not the fork's trick
  any more* — any =settings != null= skips it, which is what this plan does.
- Upstream deleted the =user.json= write. Recent AGH wants =auth.users= with a
  bcrypt hash in the yaml, so the fork's =passwordFile= path can only ever look
  configured while leaving the UI unauthenticated.
- Upstream now sets =DynamicUser = true=, which removes the persistent
  =adguardhome= user the fork creates — and an age secret owned by
  ="adguardhome"= would not be readable by the service anyway. So the
  agenix-+-overlay-+=extendModules= route is not merely heavy, it is broken.

So: do not import it. If the UI needs a password, declare
=settings.auth.users= with a bcrypt hash — no fork, no agenix, no overlay, no
rekey. The trade is a crackable bcrypt hash in git for a router admin UI; if that
is unacceptable, keep loopback + ssh and stay unauthenticated.

Both the fork and =modules/adguard.nix= are dead code: the only reference was the
commented-out =adguard= stanza in =hosts/default.nix=, and that stanza sets
=services.adguardhome-with-user.*=, so the two go together. *Both files and that
stanza are now deleted* (they sit in git history if unbound's ~do-query-localhost~
code ever needs reading again). =nix eval '.#nixosConfigurations' still yields
=asche dgx-spark misfit silver=, and
=.#packages.aarch64-linux.mono-gateway-system= still evaluates to a =.drv=, so
nothing that is actually deployed referenced them. =873d2f99= flagged them without
changing anything; this is the commit that did not.

* Later additions, and what they change

Both of the things on the agenda next move one line, not the design — which is
the point of the loopback hop.

** unbound as AGH's upstream

~dns.upstream_dns = [ "127.0.0.1:5335" ]~ and nothing else. Chain order is
load-bearing: it must be =dnsmasq → AGH → unbound → root=. Anything that puts
unbound *ahead* of AGH deletes filtering silently.

Copy from =modules/adguard.nix= with care (deleted; it is in git history): unbound drops loopback-sourced
queries under ~do-not-query-localhost~ (its default), so that =127.0.0.1:5335=
pair may fall through rather than work. Verify it before trusting it.

** VPN, server-side (remote access into the LAN)

AGH does not move. dnsmasq grows a listener:

#+begin_src nix
  services.dnsmasq.settings.interface = [ "br-lan" "wg0" ];   # + listen-address
  networking.nat.internalInterfaces = [ "br-lan" "wg0" ];
  networking.firewall.interfaces."wg0".allowedUDPPorts = [ 53 67 ];
#+end_src

That last line is not optional: the =:53=/=67= opens are scoped to =br-lan=, so a
tunnel peer would get routing but no DNS. It is also why binding AGH =0.0.0.0=
would have been the wrong shortcut — per-interface DNS is dnsmasq's job, not
AGH's.

** VPN, client-side (the board's own traffic through a tunnel)

This is the one that edits the plan rather than appending to it:

- "upstream = public IPs, reachable via NAT" stops being true, and plain-UDP DNS
  either goes to the provider's resolver or leaks around the tunnel with no
  kill-switch. It makes decision 1 a DoH/DoT decision.
- ~networking.nat~ gains a second masquerade path and ~/etc/resolv.conf~ stops
  meaning what it means today (same reason =resolveLocalQueries = false= is fine
  now, and the same reason a =tailscaled --accept-dns= would rewrite it).
- On this board a tunnel is not just =services.*=: the Phase-5.6/5.8 kernel
  patches in =hosts/mono-gateway/default.nix= exist because policy-based IPsec
  SAs were being handed to cmm and breaking ESP, and =docs/mono-gateway-build-plan.org=
  measures tunnels at *software* speed because the FMan offload does not cover
  tunnel interfaces. WireGuard is the cheap path; strongSwan inherits the kernel fight.

** unbound + a VPN client, together

Mostly counterproductive: recursion through a tunnel is visible to that tunnel's
network anyway, costs root-server latency, and buys nothing a trusted DoH
upstream does not already buy. Pick one as "who I ask last".

Suggested order: AGH now → WG remote access → (only on a real reason) a VPN
client → unbound last, and only if the client stays off.

** Client names in the query log

The log identifies clients by IP today, not by machine — and it is not that AGH
lacks the hook. All the discovery sources are already on:

#+begin_src yaml
clients.runtime_sources: {arp: true, rdns: true, dhcp: true}   # whois too
dns.local_ptr_upstreams: []      # nothing to ask for PTR of 192.168.1.x
dhcp: {enabled: false}           # so no lease file is read
#+end_src

and the result is uniform:

#+begin_src bash
ssh root@192.168.1.1 'curl -s localhost:3000/control/clients | head -c 300'
# {"clients":null,"auto_clients":[{"ip":"192.168.1.180","name":"","source":"ARP"}, …

ls -l /var/lib/dnsmasq/dnsmasq.leases   # present, 1.4 KB, one filesystem away
#+end_src

=ARP= wins by default because =rdns= has nowhere to ask and the =dhcp= source has
no path. Two fixes, neither tested here:

1. =dns.local_ptr_upstreams = [ "127.0.0.1:53" ]= — dnsmasq answers PTR for every
   lease it owns, so names come back from the one thing that actually knows the
   answer. That is the co-location upside, and it is a rebuild rather than a
   second source of truth.
2. give the =dhcp= source a lease path — a second copy of the same facts, in the
   block that also holds AGH's own (disabled) DHCP server, so read the keys
   carefully before setting anything there.

Names are what the log is actually for, so this is worth doing once the filtering
is quiet — and it is not a reason to move AGH anywhere else.

** Shipping the log off the board

Not this plan. AGH has no push, so the design is to pull =GET /control/querylog=
from the log box on a timer (=/control/querylog_search= 404s on 0.107.71); the
rest of the reasoning and the alternatives are the agenda item linked in
*Cross-links*. What this file does own is the two facts that pull design has to
survive: the retention interval below, and the fact that the rows are keyed by IP
until 1 above is done.

* Known limits

- `shortcut: filter lists update on AGH's own daily timer over HTTPS, so a board
  without WAN egress serves an empty block cache; upgrade to a nix-provided cache
  dir (or a timer-fed fetch) if filtering must work with eth2 dark.`
- *The query log file rotates far more slowly than the shipping plan assumes.*
  Shipped is =querylog.interval: 2160h= — 90 days — with =size_memory: 1000=
  matching the ring. =data/querylog.json= is a file that almost never rotates:
  fine to poll, but declare =querylog_interval= if 24h is what the design wants,
  and choose the retention rather than discovering it later.
- No =blocking_mode= is declared, so AGH's default (NXDOMAIN) applies.
  =refused=/=null_ip=/=custom_ip= exist, but the exact spelling is
  version-dependent — and the module's =checkPhase= runs
  =AdGuardHome -c … --check-config=, so a wrong value fails the *build*, not the
  router. That is also the fastest way to learn what this AGH accepts.
- ~services.adguardhome~'s *module* is 25.11's too, not ours, and whether it maps
  =host=/=port= onto =http.address= or the old =bind_host= keys depends on the
  schema version that release carries. The Phase-1 build answered that: at
  =schema_version: 32= the yaml carries =http.address: 127.0.0.1:3000=. What is
  still only provable on the box is that the bind actually took:
  ~ss -ltnp | grep 3000~ after the deploy — =0.0.0.0:3000= there means it did not,
  and the firewall is the only thing left.
- The AP's AGH is installed and inert for DNS, but not free: if its init service
  is enabled it still fetches list updates and writes to the flash. Once the
  board's AGH is working, remove the package and its service there — an
  =openwrt/routers/e8450-ap.nix= decision, same class as leaving its dnsmasq
  running.
- Declaring =filters = [ ]= while adding lists in the UI is a slow wipe: the
  declarative key wins the merge and replaces the list on the next rebuild
  (=yaml-merge= replaces lists, verified). Fix and options in *2.6*, and the
  declarative form in *3.1*.
- *Rule-list membership is a fact about the day it was measured.* The 185,488
  rules and the four blocked domains in 3.3 are from a download on 2026-10-17.
  Lists are re-fetched daily; do not treat that table as a permanent oracle, and
  re-run both directions of it after any long gap rather than trusting the
  numbers.
- *Allowlist persistence is unknown.* UI user rules land under
  =/var/lib/AdGuardHome/data/filters/=, not in the yaml, so whether one survives
  a rebuild has not been tested. Lever (1) in *3.4* is the known-good response
  until that is answered.
- *The generated yaml does not prove the DNS bind.* =dns.port= is the key
  0.107.71 reads; =bind_port= is accepted, ignored, and leaves =:53=. That is the
  one Phase-1 blind spot the run had to catch (gen 21 crash-looped), so after any
  change here the check is ~ss -lunp | grep :5354~ on the board, not the yaml.
- *AGH is advisory today, not a gate.* dnsmasq still reads ~/etc/resolv.conf~, so
  when 5354 refuses it falls back to the ISP resolvers — observed as
  "external names still resolved" while AGH was down. Good news: a dead AGH costs
  filtering, not resolution. The cost: filtering is not guaranteed, and any
  decision about DoH (1) or a redirect (3) has to account for a path that already
  bypasses AGH inside dnsmasq itself. See *Decisions still open*.
- ~blocking_mode = "refused"~ would be quieter than NXDOMAIN but tells a probing
  client *that* it was blocked rather than *that it does not exist*. Not declared
  here, so NXDOMAIN applies; flip it deliberately if that ever matters.
