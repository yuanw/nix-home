* Overview

The Mono Gateway Development Kit (NXP LS1046A, 4×Cortex-A72, 8 GB ECC, 32 GB eMMC,
3×1GbE + 2×10GbE SFP+) runs NixOS via the =we-are-mono/nix= flake. This plan covers:

1. Where to build (x86_64 Linux, DGX Spark, or on-device)
2. How to build (cross-compilation vs native, per-package vs full image)
3. How to flash and verify each gateway function

Vendor-supported OSes for this board are Debian/Ubuntu, OpenWrt, and OPNsense.
NixOS is a community port (=we-are-mono/nix=), so vendor kernel/firmware changes
land there first and our flake must re-pin deliberately.

See *[[#field-notes][Field Notes]]* for findings from non-NixOS use of the same hardware.

** Build Modes Offered by the Flake

| Mode | Command | Target System | Build Host |
|------+---------+---------------+------------|
| Cross-compiled image | =.#packages.aarch64-linux.rootfsImage= | aarch64 | x86_64 |
| Native NixOS config | =.#nixosConfigurations.gateway-native= | aarch64 | aarch64 |
| Cross NixOS config | =.#nixosConfigurations.gateway= | aarch64 | x86_64 |
| Individual package | =.#packages.aarch64-linux.<pkg>= | aarch64 | Either |
| **This repo's image** | =.#rootfsImage= | aarch64 | DGX Spark (native) |

Note: upstream's =packages.aarch64-linux.rootfsImage= is the *cross* config
(=gateway=, which hard-codes =nixpkgs.localSystem = x86_64-linux=). It is the
right entry point from an x86_64 host and wrong on the DGX Spark. Our package of
the same name wraps =gateway-native= instead, so =nix build .#rootfsImage= does
the native thing wherever it is run.

* Integration Architecture

The =we-are-mono/nix= flake is wired as a [[file:../flake.nix][flake input]] (=mono-nix=) in this
repo. Its rootfs image for the Mono Gateway DK is re-exported as
=rootfsImage= under =packages.aarch64-linux= (the previous name
=mono-gateway-image= is kept as an alias):

#+begin_src nix
# flake.nix (simplified)
inputs = {
  mono-nix.url = "github:we-are-mono/nix";  # NO nixpkgs.follows
  ...
};

perSystem = { system, pkgs, inputs, ... }: {
  packages = {
    # ... other packages ...
  } // (if system == "aarch64-linux" then {
    rootfsImage = inputs.mono-nix.nixosConfigurations.gateway-native.config.system.build.rootfsImage;
    mono-gateway-image = rootfsImage;  # old name, still works
  } else { });
};
#+end_src

Key design decisions:

1. **Self-contained nixpkgs** — =mono-nix= does NOT use =inputs.nixpkgs.follows=.
   The mono kernel patches (6.12.49, NXP fork) target nixpkgs 25.11; our
   =nixos-unstable= churn would break them. The upstream flake pins its own
   revision.

2. **Native aarch64 only** — =rootfsImage= is only exposed for
   =aarch64-linux= (= system == "aarch64-linux"). Building from macOS or
   x86_64-linux gives "attribute missing". Use the upstream flake directly for
   cross-compilation (see Option A below).

3. **=gateway-native=, not =gateway=** — The upstream flake offers two NixOS
   configs: =gateway= (forces cross-compilation from x86_64) and
   =gateway-native= (native aarch64). We use =gateway-native= since we build on
   the DGX Spark (aarch64).

4. **Pinned by flake.lock** — The =mono-nix= revision is pinned in our
   [[file:../flake.lock][flake.lock]]. Run =nix flake update mono-nix= to pick up upstream changes
   deliberately, not by accident.

* Phase 1: Set Up the Build Environment

The =rootfsImage= package is available in this repo. Three ways to build
it:

** Option B (Default): Native Build on DGX Spark

The DGX Spark is an aarch64-linux machine (Grace CPU, 128 GB RAM, 20 ARM
cores) — builds natively with no cross-compilation overhead. This is the
primary build target.

#+begin_src bash
# On DGX Spark (SSH in) — the sync'd build tree, NOT /etc/nixos
ssh yuanw@dgx-spark.local
cd nix-mono        # created by `just mono-gateway-sync`; /etc/nixos is a stale
                   # deployed copy with no mono-nix input
nix build .#rootfsImage -L
#+end_src

Or from macOS via justfile:

#+begin_src bash
just mono-gateway-build      # builds on dgx-spark via SSH, leaves result/ there
just mono-gateway-fetch      # rsyncs result/ to ./result-mono-gateway locally
just mono-gateway-serve      # serves result/ via HTTP for the mono to curl
#+end_src

** Option A: Cross-Compile from x86_64 Linux

Use when the DGX Spark is unavailable. Clone =we-are-mono/nix= separately on any
x86_64 Linux machine with Nix:

#+begin_src bash
cd /tmp
git clone --depth 1 https://github.com/we-are-mono/nix.git
cd nix
nix build .#packages.aarch64-linux.rootfsImage -L
# Takes ~2-4 h first build (kernel cross-compiles under QEMU)
#+end_src

** Option C: On-Device Build (after initial flash)

Once NixOS is booted on the Mono Gateway itself, incremental updates build
natively on-device:

#+begin_src bash
# On the Mono Gateway (once NixOS + nix-daemon are running)
nix build .#nixosConfigurations.gateway-native.config.system.build.toplevel
nixos-rebuild switch --flake .#gateway-native
#+end_src

* Phase 2: Initial Build — Full Rootfs Image

Build from this repo using the =rootfsImage= package (aarch64-linux
only). This references =we-are-mono/nix= via the pinned flake input.

** Build on DGX Spark (Default, Recommended)

#+begin_src bash
# On DGX Spark (or via SSH)
ssh yuanw@dgx-spark.local
cd nix-mono
nix build .#rootfsImage -L
#+end_src

Or from macOS via justfile:

#+begin_src bash
just mono-gateway-sync       # rsyncs the working tree to ~/nix-mono on the Spark
just mono-gateway-build      # builds there via SSH (runs sync first)
just mono-gateway-fetch      # rsyncs result to ./result-mono-gateway
#+end_src

Output: =result= → ext4 image. =result= is a symlink to one =.img= file, not a
directory. Measured on the DGX Spark (2026-10-11): 1.5 GB, 561 store paths, and
the build took about a minute because the closure was already in the store/cache
-- a fresh build host will be far slower than that.

** Inspect the Image

sudo mount -o loop,ro result /mnt/mono-rootfs

ls -la /mnt/mono-rootfs/etc/                # config files (cdx_cfg.xml, etc.)

The =/etc= / =/bin= difference is cosmetic for us: the image is populated only by
the extlinux command, and NixOS creates those paths at first activation —
=install -m 0755 -d /etc= in =init=, then =mkdir -p /bin= plus the =binsh=, =etc=,
=var=, =usrbinenv= activation snippets. Booting uses absolute store paths and
=init=/nix/store/.../init=, so nothing depends on them existing in the image. Upstream's
diagram describes the install-cd layout, not this rootfs builder.

* Phase 3: One-Time U-Boot Setup

Before flashing NixOS, the Mono Gateway must have the correct U-Boot environment.
This is a one-time operation done over UART console on the board.

** Connect UART

- Console is the **USB-C UART** port, 115200 8N1. It is *not* the USB-C data port and
  not the power port — see the panel order below. FTDI chips enumerate natively on
  macOS as =/dev/cu.usbserial-*=.
- Boot the board into U-Boot and hit any key during the countdown.
- Panel order, left to right: =USB-C power | USB-C (data) | USB-C UART | eth1 | eth2
  | eth0 | eth3 SFP+ | eth4 SFP+=. So =eth0= is the **third** RJ-45. The case labels
  match what the OS reports; identify a port by link state, not by what sits next to
  it — there are two reset buttons, and the first is described as being "near the USB
  and network ports", i.e. near all of them.
- Status LED during boot: green = hardware self-test passed, red = a test failed (U-Boot
  names the chip), orange pulsing = Recovery Linux, white = OpenWrt. One glance answers
  "is the board alive" without any network.

** Set U-Boot Variables

#+begin_src
setenv scriptaddr 0x80000000
setenv bootcmd 'sysboot mmc 0:1 ext2 ${scriptaddr} /boot/extlinux/extlinux.conf'
saveenv
#+end_src

** What This Does

- =scriptaddr=: memory address where U-Boot loads extlinux.conf
- =bootcmd=: tells U-Boot to read extlinux.conf from eMMC partition 1 (ext2 fs type
  works on ext4) and boot from it
- =sysboot= reads extlinux.conf, which NixOS generates dynamically per-generation

** How a Stale Environment Looks

Untouched vendor env boots =/boot/Image.gz= + =mono-gateway-dk-sdk.dtb=, then
=kernel.itb=, fails with =ERROR -91: can't get kernel image!=, falls through an SPI-NOR
read and lands in **Recovery Linux**. This is indistinguishable from a failed flash if
you are only looking at the network. A board that drops into Recovery on every reset,
with a correct filesystem on =mmcblk0p1=, is an env problem — apply the section above.

* Phase 4: Flashing the Image

** Boot into Recovery Linux

The board must be running Recovery Linux (the Yocto-built recovery image stored in
the firmware partition) to flash the rootfs. **It never starts by itself**: interrupt
the U-Boot countdown and run:

#+begin_src
=> run recovery
#+end_src

This is the hard dependency on the serial console — there is no network path into
recovery, and Recovery Linux brings up no interface and takes no address on its own.
Flashing from inside OpenWrt is not an alternative: its root is =mmcblk0p1=, the same
partition you are about to overwrite.

Interface names are stable across the three images (U-Boot, OpenWrt, Recovery Linux),
and Recovery Linux's =eth0= is =dtsec0=.

#+begin_src bash
# On the Mono Gateway in Recovery Linux
ip link set eth0 up
ip addr add 10.0.0.199/24 dev eth0
ip route add default via 10.0.0.1 dev eth0
#+end_src

** Serve the Image from Build Machine

#+begin_src bash
just mono-gateway-serve     # makes rootfs.img and serves it on :8000
#+end_src

=just mono-gateway-fetch= instead copies the image to this Mac (needs =-L=,
since =result= is a symlink into =/nix/store=).

Note: =result= is a symlink to a file in =/nix/store=, and python >= 3.11
=http.server= refuses to serve files whose =realpath= escapes the served
directory (404). Hence the dereferenced =rootfs.img= copy; the same trick applies
if you serve by hand — =cp -L result . = before starting the server.

Two things this page did not say, learned the hard way:

- Serve from a directory that contains **only** the image (hardlink it in). Serving
  the repo root puts =secrets/= on an HTTP listener, and =--bind 10.0.0.1= keeps it
  off the LAN but does nothing about the directory listing.
- macOS ships =openrsync=, which copies =result= as a *symlink* unless you pass =-L=,
  leaving you with a 55-byte file and no error. Same footgun as the =just=
  =mono-gateway-fetch= note above, different tool.

** Flash from Recovery Linux

#+begin_src bash
# On the Mono Gateway (Recovery Linux)
curl -O http://10.0.0.1:8000/rootfs.img   # replace with your build machine's IP
dd if=rootfs.img of=/dev/mmcblk0p1 bs=1M  # partition 1 only — SAFE (not raw device)
sync
reboot
#+end_src

** Safety Notes

| Command | Writes to | Safe? |
|---------+-----------+-------|
| =dd if=result of=/dev/mmcblk0p1= | Partition 1 (rootfs) only | ✅ Yes — firmware at offsets 0-32 MB untouched |
| =dd if=result of=/dev/mmcblk0= | Entire raw device | ❌ Destroys firmware, bricks board |

Only ever write to =/dev/mmcblk0p1= when flashing NixOS.

** Flashed (2026-10-11) — First Success

One clean run end to end, for the numbers:

| Step | Result |
|--------------------------------------+-----------------------------------------------------|
| Image | 2,075,000,832 B logical, 1.51 GiB allocated (sparse ext4) |
| =curl= in Recovery | 1978 MB in 17 s, 112 MB/s ≈ 890 Mbps, i.e. 1GbE line rate |
| =dd= to =mmcblk0p1= | =bs=1M=; returned in ~5 s (write-back), so =sync= before rebooting |
| Read-back verify | =dd if=/dev/mmcblk0p1 bs=4096 count=506592 |= =md5sum= → matches source |
| Boot | extlinux menu → kernel 6.12.49 → systemd multi-user, sshd active |

Verification discipline matters more here than anywhere else in this plan, because two
failure modes look like success:

- =head -c <huge> /dev/blockdevice= prints nothing on BusyBox and the pipe's =md5sum=
  returns the digest of *empty input* (=d41d8cd9...=). A read-back check using it proves
  nothing. Use a block size that divides the image length exactly (=4096 × 506592=).
- A serial console echoes what you type, so watching for a marker like =echo DD-OK= in
  the log tells you you typed a command, not that it finished. Match on text the board
  generates, not text you echoed.

* Phase 5: Verify Each Gateway Function

After the board reboots into NixOS, verify each function. Connect via serial console
(default: =root@ttyS0=, no password) or SSH after configuring networking.

** Configuration Layer and Deployment

Upstream's =gateway-native= leaves every interface unconfigured -- with nothing
declared, NixOS just enables DHCP everywhere, which is why a board on a direct link
sinks to =169.254/16= after a reboot and looks unreachable. Our own settings live in
=hosts/mono-gateway/default.nix= and are attached with:

#+begin_src nix
inputs.mono-nix.nixosConfigurations.gateway-native.extendModules {
  modules = [ ./hosts/mono-gateway/default.nix ];
};
#+end_src

=extendModules= rather than re-importing the modules, so upstream's overlay, module
list and 25.11 nixpkgs pin are inherited and bumping =mono-nix= cannot drift. Build the
closure and switch the running board in one step:

#+begin_src bash
just mono-gateway-redeploy   # build on dgx-spark, copy via this Mac, switch in place
#+end_src

Cheaper than re-flashing: the closure reuses the ~561 store paths already on the eMMC,
so a config change typically moves a few kilobytes. The copy is relayed through the Mac
because dgx-spark has no route to =10.0.0.0/24=.

*** Generations and rollback

A deploy registers a profile before activating, which is not optional: =switch-to-configuration
alone never creates a =system= profile, so with the plain recipe the board sits at *zero*
generations and =nixos-rebuild list-generations errors with =no profile 'system' found=. Once
profiles exist, extlinux emits one boot label per generation, so rollback is visible at the
console menu and survives a power cycle.

#+begin_quote
*nixos-rebuild cannot be used on the board.* =nixos-rebuild switch --rollback= nix-builds its
own wrapper from =<nixpkgs>= and fails on DNS, because this board is air-gapped by design.
Roll back with the primitives, which is what =just mono-gateway-rollback= does — =nix-env
--switch-generation= then =switch-to-configuration switch=. Note this re-points at the older
generation rather than creating a new one, so running it twice is idempotent.
#+end_quote

Verified 2026-10-12: gen 1 → canary deploy → gen 2 → rolled back → *rebooted*, and the board
came up on gen 1 (t+28 s). A config differing only by a comment rewrites to a generation
pointing at the same store path — deterministic builds, not a broken profile.

#+begin_quote
*Deliberate:* the board is air-gapped -- on-link route only, no gateway, no DNS. Closures
are pushed, never pulled. Do not add =defaultGateway=/DNS to "fix" it; WAN addressing
belongs to the cutover (Phase 6 of the agenda). On-device building stays deferred.
#+end_quote

** 5.5 Throughput Testing

Connect two machines to test routing throughput:

#+begin_src bash
# On a client machine connected to dtsec0 (1GbE):
iperf3 -c <gateway-ip> -t 30
# Expected: ~940 Mbps (1GbE line rate minus overhead)

# On a client connected to dtsec3 (10GbE SFP+):
iperf3 -c <gateway-ip> -t 30
# Expected: ~9.4 Gbps (10GbE line rate minus overhead)

# Bidirectional
iperf3 -c <gateway-ip> -t 30 -R
# Expected: ~4-8 Gbps total bidirectional

# UDP test
iperf3 --udp -b 1G -c <gateway-ip> -t 30
#+end_src

The real pass criterion is CPU idle, not throughput: on the same hardware, line-rate
gigabit NAT + nftables + conntrack used ~0.3–2.6% CPU, and 10G line rate was
confirmed under a different OS. High CPU during iperf means the ASK fast path is
/not offloading — go back to 5.6.

#+begin_src bash
top -bn1 | head -20       # during iperf: expect ~1-3% CPU at line rate
#+end_src

** 5.7 CAAM Crypto Accelerator

CAAM is built into the kernel — verify it's active and available for XFRM offload:

#+begin_src bash
# Check CAAM in crypto API
cat /proc/crypto | grep caam -A 5
# Should show: driver: caam-...

# Check CAAM job rings

Per the [[file:/Users/yuan/org/denote/20250913T140000--mono-gateway-dk-opnsense-vs-nixos-evaluation.org][evaluation document]], three of four gaps are trivially fixable.

** Fix 1: PCF2131 RTC (1 line)

Add to =pkgs/kernel/defconfig=:

#+begin_src
CONFIG_RTC_DRV_PCF2131=y
#+end_src

The driver exists in Linux 6.12; just not enabled in the NixOS defconfig.

** Fix 2: TMP431 Thermal Sensor (1 line + rebuild)

Add to =pkgs/kernel/defconfig=:

#+begin_src
CONFIG_SENSORS_TMP431=m
#+end_src

The tmp431 driver is in mainline =drivers/hwmon/tmp431.c= — no custom patch needed.

** Fix 3: CAAM — Already Done

CAAM is fully built-in to the kernel. XFRM will auto-offload to CAAM.

Not trivial. Requires porting the =mwifiex= driver (~30 files) and the =dpaa_wifi=
bridge from the OPNsense-deps repo. Defer unless WiFi on the Mono Gateway is a
hard requirement.

* Reference: Field Notes
:PROPERTIES:
:CUSTOM_ID: field-notes
:END:

External, non-NixOS use of the same Mono Gateway DK dev kit:
[[https://www.youtube.com/watch?v=afUdNdhUUeE]["I'm not happy with any router OS, so I'm trying something else"]]. They use
Debian + systemd-networkd + nftables + resolved, automated with Ansible — a
different toolchain, so the config work does not transfer to NixOS. These
hardware findings do:

| Finding | Use here |
|---------+----------|
| Packet offload is transparent on Linux: =ip=, =ip route= and nftables are all pushed to hardware | Confirms our architecture — no userspace fast-path config needed beyond 5.6 |
| 1 Gbps NAT/firewall/conntrack at ~0.3–2.6% CPU; 10G line rate confirmed | Pass criterion for 5.5 |
| Offload may not apply to tunnel interfaces | Caveat for 5.8 IPsec and Phase 6 Fix 3 |
| Vendor port order 1,2,0,3,4 is a known bug they plan to fix | Note in 5.3 |
| Vendor OS list: Debian/Ubuntu, OpenWrt, OPNsense | Context in Overview |
| Board runs from USB-PD, tiny fan, not warm at line rate | Baseline for 5.9/5.14 thermal checks |
| Vendor OpenWrt defaults =br-lan= to 192.168.1.1/24, bridged over eth0/eth1/eth2 | Landmine: same address as the house router. Never bridge these ports onto the LAN until the address changes |

Not applicable to us: their systemd-networkd =.network=/=.netdev= files, their
Ansible/Jinja generation pipeline (NixOS already gives us this), and their
rescue-port trick (spare 1GbE port running IPv6 ULA + mDNS so the box is always
reachable at =gateway.local= — worth stealing later if we ever serial-lockout).

* Build Diagnostics Quick Reference

| Symptom | Likely Cause | Fix |
|---------+-------------+-----|
| Kernel build fails in =linuxManualConfig= | Missing defconfig option | Check =pkgs/kernel/defconfig= for required NixOS assertions (=CONFIG_AUTOFS_FS=y=, =CONFIG_CRYPTO_USER_API_HASH=y=) |
| FMC build fails | CRLF line endings | Should be handled in =prePatch= but check =source/*.cpp= for =^M= |
| CDX build fails: =ncsw_config.mk= not found | SDK headers missing | Check =sdk-headers.nix= has extracted the FMan UAPI headers; CDX =Makefile= patches for direct =ccflags-y= |
| CDX calls =/usr/bin/dpa_app= at runtime | Hardcoded path | Check =substituteInPlace= in =pkgs/cdx/default.nix= pointing to Nix store path |
| CMM fails to start | =/dev/cdx_ctrl= not found | CDX module not loaded; check =load-ask-modules.service= runs before =cmm.service= |
| Boot fails: kernel panic on rootfs | Wrong partition | Confirm flashed to =/dev/mmcblk0p1=, not raw =/dev/mmcblk0= |
| Boot fails: no serial console | Wrong kernel param | Check =console=ttyS0,115200= in =kernelParams= |
| SFP+ LEDs not working | sfp_led module not loaded | Check =boot.extraModulePackages= includes =mono-gateway-sfp-led= |
| nftables fails | Missing =CONFIG_NFT_*= in kernel | Add missing nftables options to =defconfig= |
