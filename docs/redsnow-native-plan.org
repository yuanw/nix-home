Known trap (found during eval, now commented in the module): nixpkgs
carries an *upstream* =python3.13-exllamav3= (1.5.0, x86_64-only).

exactly how the tensorfold unit handles the same situation.

** DONE Phase 1: Build on target
:PROPERTIES:
:CUSTOM_ID: build-target
:END:

=colmena apply= (=buildOnTarget = true=) runs the real AOT CUDA compile on
the Spark (~15–20 min for =exllamav3_ext=, =MAX_JOBS=16=). Build first so a
compile failure never touches the running system:

#+BEGIN_SRC shell
just colmena-spark-build    # colmena build --on dgx-spark
#+END_SRC

Verify the extension landed before applying (on the Spark; the build
products are in the store after =colmena-spark-build=):

#+BEGIN_SRC shell
ssh yuanw@dgx-spark.local
nix build /etc/nixos#nixosConfigurations.dgx-spark.pkgs.python313Packages.exllamav3 -o /tmp/exl
find -L /tmp/exl -name 'exllamav3_ext*.so'   # expect: .../site-packages/exllamav3/exllamav3_ext.*.so
#+END_SRC

A *missing* .so means setup.py built pure-python — the classic trap is
torch not importable in the build sandbox, so the =CUDAExtension=
was skipped (=EXLLAMA_NOCOMPILE= unset but =precompile and not torch=
false). Fix in =packages/red-snow/default.nix= (=build-system=,
=dependencies.torch=), not by adding a JIT fallback: the whole point of
the AOT build is that first start never compiles.

Missing CUDA *headers* (the bitsandbytes/cusparse class: =cusparse.h:
No such file or directory=) means a redist package split its headers into
another output — extend the =cudaHome= merge list. The import smoke test
is Phase 3 itself: =serve_glm.py= imports =exllamav3_ext= before the
first "Native API listening", so no separate import check is needed.

*** Why the build was fast: reverted =57c29f89=

The =wip= commit =57c29f89= bumped the main =nixpkgs= input
(=c59305bab2= → =151fa4e8dd=). That bump left torch's drv unchanged but
pulled a *new* =torchvision= that depends on extra CUDA-library outputs;
torch's =cxxdev/dist= outputs had been GC'd, forcing a full torch source
rebuild. On this host that rebuild crashed twice in different CUDA
compiler subprocesses (=ptxas= SEGV at =ScatterGatherKernel.cu.o=; =cicc=
SEGV at =IGammaKernel.cu.o=) — no cache carries the bleeding-edge
aarch64 torch, so substitution was not an option.

=flake.lock= was restored to =57c29f89^= (only the nixpkgs pin reverted;
=flake.nix= inputs unchanged). Verified under =c59305bab2=:

- torch = =xrhfxz636g5xfh16rlakavvhs248fzrn= (running system's drv)
- torchvision = =g0k8mjhk0xdnrx9im3cf455msb3a99lg= (running system's drv)
- exllamav3 drv byte-identical to the new-pin build (=jnfbdzkwa808vy5b0gbw3c0n0jzp4pbj=)

so the revert reuses the already-built torch/torchvision and invalidates
nothing previously built. Self-check runnable on the Spark:

#+BEGIN_SRC shell
nix-store --check-validity /nix/store/v0bn27hh6gjwn0qq3hksfik65jjcd0v4-nixos-system-dgx-spark-26.11pre-git
find -L /nix/store/srd7f4bgrx7g6xppblwwy8pv297wrjjl-python3.13-exllamav3-1.5.1.post1 -name 'exllamav3_ext*.so'
#+END_SRC

Re-bumping nixpkgs is a separate task: if the newer pin is wanted later,
the torch =cxxdev/dist= outputs must be rebuilt (or capped to =sm_121=)
*and* an aarch64 cache found. Deferred; not required for RED-SNOW.

3. Tool calls:
   #+BEGIN_SRC shell
   curl -s http://dgx-spark.local:8899/v1/chat/completions \
     -H 'Content-Type: application/json' \
     -d '{"model":"RED-SNOW-5.3-FLASH-EXL3-2.49","messages":[{"role":"user","content":"Weather in Paris for 3 days? Use the tool."}],"tools":[{"type":"function","function":{"name":"get_weather","parameters":{"type":"object","properties":{"city":{"type":"string"},"days":{"type":"integer"}},"required":["city"]}}}],"chat_template_kwargs":{"enable_thinking":false}}' \
     | jq '.choices[0] | {finish_reason, tool_calls: .message.tool_calls}'
   #+END_SRC

Acceptance (the recipe's measured numbers, single stream, MTP 2 drafts):

| Check | Target |
|-------+--------|
| Long outputs (≥1,000 tok) decode | ~34 tok/s median (p10–p90 32.9–34.9) |
| Prose decode | ~24 tok/s |
| MTP draft acceptance (long) | ~84% |
| MTP draft acceptance (prose) | ~47% |
| Tool call | =finish_reason= = =tool_calls=, parsed =get_weather= |

A materially slower decode (≈ container-era, not 2×) means the page-cache
drops are not landing — check the unit runs as root and
=/proc/sys/vm/drop_caches= writes appear in the journal.

** TODO Phase 4 (optional): Spot regression vs Spark-Bench 85.1
:PROPERTIES:
:CUSTOM_ID: regression
:END:

The repo published a full Spark-Bench run (80 tests, 2 repeats, thinking
off, uncapped output, TrueScore 85.1) for the *container* deployment. The
native serving path changes none of the model bits (same engine commit,
same quant revision, same flags), so a full re-bench is a redundancy check —
but a spot run is cheap insurance against a silent environment difference
(nixpkgs torch vs the =26.07= container image):

- Same sampling as the report: temp 0.7 / top_p 0.95 / min_p 0,
  thinking off.
- Compare per-domain quality (agentic, code, instruction) — these move
  little with engine-level noise; treat ±0.3 aggregate as noise (the
  report's own caveat).
- Decode speed *should match the container exactly*: same kernel commit,
  same =sm_121= compile — differences point at the environment (torch
  version, CUDA 13.2 vs the image), not the server.

Skip entirely if the Phase 3 smoke numbers match the container baseline.
